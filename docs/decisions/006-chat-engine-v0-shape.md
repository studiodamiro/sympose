# 006 — Chat engine v0: turn handling, grounding, sessions, and what's deliberately out

## Context

`docs/VISION.md` describes the full chat engine as one large milestone: turn handling, grounding, model routing, message queueing, sessions, continuous memory extraction, live compaction, session-close archival, MCP tool-calling, skills, folder definitions, and Samantha's real soul content. This project's standing rule is an ADR written immediately before the feature it covers, not upfront for a whole roadmap — so this record covers only the first slice: a working, grounded, session-logged turn loop reachable from a real channel, with everything else named and explicitly deferred rather than silently absent.

Two things were settled before this slice's code was written, worth recording here since they shape the design:

- The existing Textual CLI mock (`sympose/cli/`, ADR 005) was live-verified — via a real `tmux` run, not just a read-through — to already have a fully working persistent input, word-by-word streaming reveal, `/`-command Tab-cycle autocomplete, a numbered `/model` picker that live-updates the header, and a clean `/quit`. `VISION.md`'s original sequencing scoped a separate small blocking-loop "minimal CLI" to ship alongside the engine, with persistent input deferred as later polish; that ordering is superseded now that the persistent-input UX already exists and is tested, so this slice wires the existing mock to real engine calls instead of building a second CLI.

  This does **not** fully retire the case for a separate, non-Textual CLI entry point. ADR 005 gave a second, independent reason for one: staying scriptable/pipeable (stdin piped in, output piped out) without pulling in a full TUI framework — a concern about deployment footprint, not about blocking vs. persistent input, and nothing this slice's live verification touched. That need is real and unaddressed, just not built in this slice; it stays open for a later slice if scripted/piped use is actually wanted, rather than being decided away by omission.
- `docs/decisions/007-litellm-for-model-calls.md` covers the model-call/dependency side of this design (litellm, the `ollama_chat/` prefix, the default local model, the settings key). This record assumes that decision and doesn't re-argue it.

## Decision

A new `sympose/engine/` package, one file per concern (matching `sympose/cli/`'s existing split and this repo's 200-LOC-per-file guideline):

- **`grounding.py`** — `ground(profile, user_message, max_results=5)` calls `vault_search.search_structured` (per ADR 002: reused unmodified, no change to the matcher itself), but not with just the raw message. **Live-verified against a real vault and revised mid-slice**: `search_structured` matches by checking whether the *whole* query is one contiguous substring of a note's title/tag/body. A short, note-name-like message ("Apple M2") can match that way; a real chat-shaped question ("what dev machine specs can run gemma2 comfortably per the vision doc") essentially never will, even when the exact answer sits verbatim in a note — confirmed live: that literal question returned zero grounding hits against `VISION.md`, which contains the answer word-for-word. So `ground()` tries the raw message first (still catches the short-message case), then each of the message's own significant individual words as separate queries against the same unmodified matcher, merging and deduping hits by `rel_path`, capped at `max_results`. This is a query-shaping change on top of `search_structured`, not a change to it or to ADR 002's decision. `max_results=5` (vs. `search_structured`'s own default of 40) because a prompt needs a handful of top matches, not a browsable list — that default is tuned for the dashboard's two-tier UI, not this call site.
- **`prompt.py`** — `build_system_prompt(profile, grounding_results)` renders each grounding hit as a labeled evidence block (title, path, snippet) plus an explicit instruction enforcing the zero-hallucination principle: only state vault facts backed by that evidence, say so when nothing matches. Degrades to a coherent prompt (no crash, instruction still present) when grounding is empty. `PLACEHOLDER_SOUL` is a minimal inline system-prompt fragment — enough persona identity to exercise the pipeline, deliberately not Samantha's real voice-from-*Her* content, which stays its own separately-scoped, later checklist item (persona shape is product writing, not engine architecture).
- **`session.py`** — a JSONL log at `sessions/<handle>/<session_id>.jsonl` (new `SYMPOSE_SESSIONS_DIR` env var, cwd-relative default, matching `profiles_dir()`/`settings_path()`'s existing convention). Line 1 is a meta object (`session_id`, `handle`, `title`, `created_at`, `updated_at`, `turns_count`); each following line is one turn (`timestamp`, `user`, `assistant`). `title` is the first ~6 words of the opening message — the smart background-model retitling legacy had is deferred. Nothing is written to disk until the first `append_turn`, which means a session opened but never used leaves no file at all — this satisfies `VISION.md`'s "a session that never got used is pruned automatically" with no separate sweep needed, as a side effect of the write timing rather than a dedicated pruning pass. `append_turn` takes an optional already-loaded `existing` session (caught on a closer look: `run_turn` loads the session to build history, and `append_turn` was independently reloading and re-parsing the same file a second time in the same turn with no correctness need to) — a bare `append_turn(handle, sid, msg, reply)` call still loads it itself, for any caller that doesn't already have it in hand.
- **`turn.py`** — `run_turn(handle, user_message, session_id=None, model=None) -> TurnResult` is a plain sync function (matching every other handler in this codebase — `server.py`'s routes are all sync `def`) that resolves the profile, loads/starts a session, grounds, assembles the prompt, calls the model, persists the turn, and returns. Its steps are separately callable functions in a fixed sequence, not inlined logic, specifically so the seam between "model call returns" and "persist and return" is visible and reusable: `VISION.md` states message queueing is an engine requirement, not just a UI one, and this is where a later queueing milestone would check for newly-arrived input before finalizing a turn. **Queueing itself is not implemented in this slice** — this is a structural note for later, not a feature now.
- **CLI wiring** — switching persona mid-conversation (`/persona`) resets `app.session_id` to `None`. A closer look caught that not doing so silently forked/lost history: sessions are stored per-handle, so an old session_id carried into a new persona resolves to *that* persona's own (empty) session directory — the model would see no history at all while a new file quietly starts under the stale id, orphaning the old persona's in-progress session. A persona switch now starts fresh, the same as a new CLI process would.

## Consequences

Grounding, personas, and settings all reuse existing, already-reviewed code (`vault_search.search_structured`, `profile.resolve_profile`, `settings_store.get`/`set`) rather than introducing parallel mechanisms — the only genuinely new surface is session storage and the model call itself (the latter covered in ADR 007).

The session log has no file lock — same read-modify-write-whole-file posture as `settings_store.set`, appropriate at today's scale (one process, one turn at a time, no queueing UX yet) but a known gap the moment queueing or a second channel can genuinely write the same session concurrently. Not hardened here; revisit when either of those actually lands. This also means `append_turn`'s cost (re-parse, then rewrite the whole file) grows with a session's total turn count rather than staying flat, and a crash mid-write (`open(path, "w")` truncates before writing) can in principle corrupt already-durable prior turns, not just the newest one — the same risk `settings_store.set` already carries for its one small file, here on a file that grows without bound for the life of a session. Acceptable for v0 at personal-conversation-length scale; a true append-only write (new turn appended as a line, meta line updated separately or reconstructed on read) is the fix if a long-running session in practice makes this cost or risk real, not designed preemptively here.

The CLI's persistent input calling a blocking model call directly would freeze the whole UI for the round-trip — `sympose/cli/runtime.py`'s `send_message` becomes `async def`, offloading `run_turn` via `asyncio.to_thread`, which is the mechanism that keeps the persistent-input UX genuinely non-blocking rather than just visually so. Further review caught that this alone isn't enough: nothing stopped a second message, submitted before the first's reply lands, from calling `run_turn` concurrently with it and racing the unlocked session read-modify-write this record already accepts as a single-turn-at-a-time design. Fixed with `app.turn_lock`, an `asyncio.Lock` serializing the engine call itself (not the composer — typing and submitting stay instant; a queued-behind message just waits at the lock before its own `run_turn` call starts, so by the time it runs it correctly sees the prior turn's already-appended history). This is a minimal safety fix, not the message-queueing milestone itself — no UI indication of "waiting," no absorption of a queued message into an in-progress turn's own context, both still deferred. Verified live/deterministically, not just by inspection: each fix in this section was confirmed by temporarily reverting it and watching its own regression test fail, then restoring it and watching the test pass again — the same discipline `docs/CHECKLIST.md`'s standing lessons already name for state-timing bugs.

Making `send_message` genuinely span an await, though, opened three more races caught in a follow-up review round, all from the same root cause — code resuming after the await re-reading *current* `app` state instead of the state this specific call was dispatched for:

- **Persona switched mid-call.** The persona-switch fix above (resetting `app.session_id` to `None`) could itself be silently undone: if persona A's call was still in flight when the user switched to persona B, A's call resuming afterward would unconditionally overwrite the just-reset `None` with A's own session_id — reintroducing the exact cross-persona session fork the switch-reset fix exists to prevent. First fixed by capturing `handle = app.persona.handle` before the lock and only writing `app.session_id` back if it still matched on resolve — a closer look then caught that a handle check alone isn't quite enough: switching away and back to the *same* persona before the in-flight call resolves matches on handle again, letting the stale call clobber the *second* switch's fresh-session reset even though no cross-persona mixup occurs. Confirmed live/deterministically (reverted, watched the new regression test fail with the exact stale-session assertion, restored). Fixed properly with `app.session_generation`, an int bumped every time a persona switch resets `session_id` — `send_message` captures it alongside `handle` before the lock and only writes `app.session_id` back if the generation is still the one it was dispatched under, which catches a same-persona switch-back the handle comparison alone couldn't.
- **Reply misattribution.** `_stream_reply`'s header (`@{persona} · {model}`) was built from `app.persona`/`app.model` read fresh after the lock — a reply generated for persona A but resolving after a switch to B would display under B's name. Fixed the same way: `handle` and the model id/header are captured once, up front, and threaded through explicitly (`_stream_reply` now takes `header` as a parameter instead of reading `app.persona`/`app.model` itself).
- **`/quit` during an in-flight call.** `app.exit()` had no awareness of an outstanding `asyncio.to_thread` call; when it resolved after teardown began, the resuming coroutine tried to mount a transcript line onto an already-detaching widget tree — confirmed live via the regression test, a real `textual.widget.MountError: Can't mount widget(s) before ... is mounted`, not just a theoretical risk. Fixed with an `if app._exit: return` check on both the success and `EngineModelError` paths after the lock.

None of this is full message-queueing UX — no "still waiting" indicator, no in-progress-turn context absorption — it's the minimum needed so the async wiring above doesn't silently corrupt state or crash when a user does something else (switch persona, switch model, quit) while a reply is still in flight, which the CLI's whole persistent-input premise explicitly invites them to do.

A few smaller correctness fixes from the same review passes: `append_turn`'s `existing` parameter first shipped behind a sentinel object (to distinguish "not passed, please load it" from "passed as `None`, genuinely new") — simplified to a plain `existing: dict | None = None` default once it was clear the distinction cost more than it bought, since the "please load it" case for a brand-new session is already cheap (a single `os.path.exists` check, not a real parse), so collapsing both cases into one is free. `load_session` now skips a line that parses as valid JSON but isn't a dict (e.g. a truncated `[1,2,3]` from a crash mid-write) instead of raising `AttributeError` from `.get(...)` on it — degrading gracefully, consistent with the "corrupt file → `None`/empty" contract its own docstring already promised. `history_as_messages(session, max_turns=0)` now returns `[]` instead of the *entire* history — `list[-0:]` is `list[0:]` in Python since `-0 == 0`, a latent landmine no current caller triggers (the only call site uses the default of 20) but a one-line, zero-risk fix once seen. `sympose/cli/mock_data.py`'s local-model `ModelOption` now imports `model.DEFAULT_LOCAL_MODEL` instead of re-typing the same string literal, per `CODE_QUALITY_STANDARDS.md`'s "a setting lives in exactly one canonical place" rule — the CLI always passes this id straight through as `run_turn`'s per-call override, so a stale duplicate here would have meant the CLI's actual running default silently diverging from the engine's own canonical one the next time someone changes `DEFAULT_LOCAL_MODEL`.

`ground()`'s per-word query fan-out is still not semantic — it's the same literal-substring matcher, just run more times against smaller, more plausible pieces of the message. A word spelled or phrased differently from how the note itself is written (a synonym, a typo, a paraphrase) still won't match. This is the same fundamental limitation ADR 002 already named for `search_structured`, now more precisely understood after live verification: the risk isn't "misses meaning-based matches," it's "misses almost everything that isn't a near-verbatim word," which per-word querying meaningfully narrows but does not remove. Worth revisiting if real use shows this still grounds too rarely — the next step up would be lower-casing/stemming-tolerant matching before reaching for embeddings, which ADR 002 already rejected for now.

A follow-up review round, after the fixes above, caught one more in-scope gap and surfaced three deeper ones that turned out to be the message-queueing milestone's own territory, not this slice's: `send_message` only caught `engine.EngineModelError` around the engine call — any other exception (a bug in `grounding`/`prompt`/`session`, none of which existed before this slice) propagated uncaught out of the Textual event handler instead of degrading to an in-transcript line like every other failure path here. Fixed with a broader `except Exception` after the `EngineModelError` case, logging the real exception and showing a generic "unexpected error" line — confirmed live/deterministically the same way as the rest of this section (reverted, watched the regression test raise a raw `KeyError` instead of showing the friendly message, restored).

One more round closed this slice out: Textual's default ctrl+q binding and its command-palette "Quit" entry both call `App.action_quit` directly — a second exit route that bypassed `/quit`'s own turn_lock check entirely, reintroducing the same hang through a different door. Fixed by overriding `action_quit` in `sympose/cli/app.py` with the same check, and having `/quit`'s own command handler simply `await app.action_quit()` instead of duplicating the logic — one place for it, not two. The same round also collapsed `send_message`'s two near-identical except-block tails into one `_show_failure` helper (before a third failure mode meant a third copy); fixed `load_session` catching `json.JSONDecodeError` per-line instead of around the whole read, so one truncated line (the exact risk `_force_exit` above accepts) no longer discards every other valid turn in the file, not just the bad one; and fixed `/persona` unconditionally resetting `session_id` even when the user reselects the persona they're already talking to. All four confirmed via the same revert-and-check discipline as the rest of this record.

Two gaps from that round are accepted, not fixed: `_force_exit` can in principle fire mid-write inside `append_turn`'s `open(path, "w")` truncate-and-rewrite, since the lock (and thus the "is a call in flight" check) is held for the write too — a narrow window (a fast local file write inside a multi-second-plus call), and the same fundamental "an already-running thread can't be cancelled" tradeoff already accepted above, just relocated; the per-line JSON fix directly shrinks its blast radius (one bad line, not the whole file). And `run_turn` returns success even when `append_turn`'s write silently failed (`settings_store`-parity, already accepted above) — `run_turn` doesn't check, so a reply can be shown as delivered while never actually persisting; consistent with the existing posture, not a new gap introduced here.

Left as documented, not fixed, since each points at genuine future work bigger than a same-slice patch: `sympose/cli/runtime.py` is now 239 lines against this repo's own 200-LOC-per-file guideline (the file grew with the fixes in this section; a split is a real follow-up, not done here to avoid re-churning a file mid-review); `ground()`'s up to-7 `search_structured` calls run sequentially with no data dependency between them, so they could run concurrently instead of stacking their latency inside `turn_lock` — real, but async-fies a currently-sync module for a cost already noted above as dominated by model inference in every live test; and the hand-rolled `turn_lock`/`session_generation`/`app._exit`-checks/`_show_failure` machinery in this file is, structurally, a narrower version of what Textual's own `@work(exclusive=True)` worker API is purpose-built for ("one in-flight async op, supersede on redispatch") — a legitimate larger refactor for whenever the next stateful concern (a second channel, model-switch-mid-call) would otherwise need its own bespoke version of the same pattern, not attempted here.

The three deeper findings from the round before, all genuinely real but all downstream of `app.turn_lock` being a *minimal safety fix* rather than actual message queueing (already flagged above as out of scope — no "still waiting" indicator, no in-progress-turn context absorption):

- **A second queued message for the same persona can still fork/orphan a session if a persona switch happens in between.** Concretely: send msg1 (task1 starts, holds the lock), send msg2 for the same persona while task1 is still running (task2 captures the current `session_generation` and blocks on the lock), then switch away and back to that same persona before task1 resolves. task1's own write-back is correctly skipped (generation mismatch, per the fix above) — but task2, once it finally acquires the lock, reads `app.session_id` live at that point, which the intervening switch reset to `None`, not task1's freshly-created session. task2 starts yet another brand-new session instead of continuing task1's, orphaning it (msg1 is not lost — it's durably in its own session file — but the conversation silently forks in two). A real fix means tracking session continuity across multiple in-flight/queued calls for the same persona, which is squarely what the message-queueing milestone needs to solve anyway (deciding how a queued message hands off from/into an in-progress turn's context); not attempted here.
- **Two turns can now stream concurrently and share one `app.reply_timer` slot.** `turn_lock` only serializes the engine call, not the post-lock word-by-word reveal — if a second queued call's engine work finishes while the first is still streaming, both `_stream_reply` timers run at once, and whichever one starts or finishes second overwrites `app.reply_timer`, so `/clear`'s explicit "stop the mid-stream timer" can stop the wrong one (or fail to stop either). Bounded in practice by `_stream_reply`'s existing `is_mounted` guard (a timer ticking against an already-cleared transcript silently no-ops rather than crashing or corrupting anything), so the actual failure mode is cosmetic — a reply's word-by-word reveal not fully completing after a `/clear` hits mid-stream — not data loss. A real fix (each streaming reply tracking its own stoppable timer instead of one shared slot) is UI-queueing work, the same category as the point above.
- **A session-file write failure is silent.** `append_turn` swallows `OSError` with a log warning, matching `settings_store.set`'s own established, already-accepted pattern in this codebase (ADR 003) for local single-user state — but it means a reply already streamed to the user as successful may never actually persist (disk full, permissions), with no user-facing indication and the next turn's history silently missing it. Left consistent with the existing `settings_store` precedent rather than given special new failure UX here; revisit only if this turns out to matter in practice, the same posture ADR 003 already took for its own analogous gap.

A further review round caught something genuinely severe in this same area, which this record does *not* leave as a documented gap — it's fixed: **`/quit` while a call is in flight didn't hang the app, it hung the whole process.** `asyncio.to_thread` runs on asyncio's own loop-managed default executor; `asyncio.run()`'s shutdown sequence explicitly drains that executor before the process can exit, and a thread already running `litellm.completion(...)` can't be cancelled once started (`concurrent.futures.Future.cancel()` only succeeds before a worker picks the work up). Confirmed live, twice: first a version using a dedicated (non-default) executor still took ~6 real seconds to quit — because the coroutine awaiting that executor's wrapped future also can't be force-unblocked by cancellation, it genuinely waits for the thread to finish regardless of which executor backs it; the real fix is `sympose/cli/runtime.py`'s `/quit` handler checking `app.turn_lock.locked()` and calling `_force_exit` (a thin, test-mockable wrapper over `os._exit(0)`) immediately, skipping graceful `asyncio`/Textual teardown entirely rather than waiting on it, confirmed live to drop quit-while-generating from several seconds (or up to `model._REQUEST_TIMEOUT_SECONDS` in the genuinely-stuck case) to about a second of ordinary terminal teardown. `sympose/cli/__main__.py` also now calls `os._exit(0)` right after `SymposeCLI().run()` returns, since Python's normal interpreter shutdown separately waits on *every* `concurrent.futures` worker thread in the process via a global `atexit` hook, not just the ones asyncio itself manages — defense-in-depth for the non-force-exit quit path, given the engine call is now dispatched through a dedicated `_ENGINE_EXECUTOR` (kept from the first attempt above) rather than `asyncio.to_thread`'s shared default one.

**Known, deliberately-not-fixed gaps surfaced during review, weighed and left as-is:**

- **`ground()`'s per-turn cost**: up to 7 `search_structured` calls (1 whole-message + up to 6 keywords) per turn, and tracing this further showed each call re-walks and re-stats every tracked vault file regardless of cache hit — `vault_paths.dirs_mtime` (the cache's own freshness check) does a full `os.walk`/`os.stat` pass every time, by design, to detect whether anything changed since the last build; only the expensive parse-and-classify step is skipped on a hit. So this is stat-only work multiplied up to 7x per turn, not 7x full re-parses — `dirs_mtime`'s own docstring already calls a single such walk "cheap even at tens of thousands of files," and every live-verified turn in this slice was dominated by multi-second model inference, not vault I/O. Not fixed here because the real fix (fetching one snapshot and classifying against it multiple times) means changing `search_structured`'s interface, which ADR 002/006 both commit to reusing unmodified — that's a deliberate, separate future change if real vault sizes or turn latency ever make this the actual bottleneck, not a preemptive refactor of already-reviewed code for a cost not yet shown to matter.
- **`sympose/engine/session.py`'s `session_path()`** hand-rolls the same "join a derived path segment, then `is_safe_path`-check it" idiom that `sympose/profile.py`'s `get_profile` and roughly eight other call sites across `vault_paths.py`/`vault_write_*.py`/`vault_trash.py` already implement identically, with no shared helper. A real duplication worth flagging, but factoring it out means touching multiple already-reviewed files well outside this slice's boundary — deliberately left as one more matching instance of an existing pattern, not introduced fresh, and better tackled as its own small, dedicated cleanup than folded into an unrelated feature slice.
- **`/clear` while a turn is still awaiting its engine call** wipes the transcript including the just-mounted "You" line — a new interleaving `send_message` being `async def` makes possible that wasn't reachable before (the pre-existing `/clear` handler already anticipated a reply mid-*stream*, stopping `app.reply_timer`, but not a reply mid-*dispatch*, before any reply text exists). The turn is still durably written to the session log regardless — this is a display-only rough edge (the eventual reply appears with no visible prompt above it), not data loss or a crash, and narrow enough (send a message, then `/clear` before any reply arrives) that it's left as a known cosmetic gap rather than added state-tracking to guard against it here.
- **`profile.py`'s `get_profile` malformed-file fallback is more consequential now than when it was written.** Pre-existing code (untouched by this slice) returns a whole-vault `{"vault_folders": ["*"]}` fallback in three cases: no profiles directory configured at all (the intended day-one default — a fresh checkout with no `profiles/` should give Samantha full access), an unsafe path, or a profile file that exists but fails to parse (bad YAML, a permissions error). The third case is new-consequential: before this slice, `get_profile`'s only caller scoped dashboard vault-*browsing* routes; now `grounding.ground` also calls it (via `run_turn`), so a corrupted `profiles/<handle>.yaml` silently widens that turn's *grounding* search to the whole vault instead of failing safe. A real gap against the "zero-hallucination, sandboxed" grounding principle, but fixing only the "corrupted file" sub-case without breaking the "no profiles dir" default-access case means splitting `get_profile`'s single fallback into two different outcomes — a behavior change to shared, already-reviewed code well outside this slice's own files, for a fault condition that requires a user's own profile file already being broken (self-inflicted, single-user, local-first tool — no other threat actor). Left as a known, documented gap rather than modified here.
- **`sympose/cli/mock_data.py` now transitively imports `litellm`** (via `from sympose.engine.model import DEFAULT_LOCAL_MODEL`, added earlier in this same record to satisfy "declared once" — re-typing the literal string would reintroduce that finding instead). A real tension between two legitimate concerns, weighed rather than silently picked: `mock_data.py` is only ever imported by this CLI package today, and the CLI as a whole already fully depends on `litellm` the moment any real message is sent (`runtime.py` imports `sympose.engine` unconditionally) — so this doesn't actually add a new hard dependency for any current caller, only couples one more file to an import that was already load-bearing for the package as a whole. Judged not worth a deeper decoupling (e.g. a separate lightweight constants module with no `litellm` import) for a cost that isn't real yet; revisit if `mock_data.py` ever needs to be importable somewhere that genuinely can't carry `litellm`.

**Correction (2026-09-23, full-backend code review):** the `profile.py` gap above undersold itself. `get_profile`'s `except (OSError, yaml.YAMLError)` catches `FileNotFoundError` too — an `OSError` subclass — so "file exists but fails to parse" and "file simply doesn't exist yet" hit the identical fallback; the entry above only named the former. That breaks the "self-inflicted, requires an already-broken file" framing this gap was accepted under: no profile has to be broken at all, just not yet created, which is the ordinary state of any typo'd or not-yet-configured persona handle — not a rare fault condition. A dedicated review agent live-verified this bypassing read, write+delete, *and* chat-grounding sandboxing against a deliberately-restricted profile, a direct hit on the "zero-hallucination, sandboxed" guarantee this same entry invokes, not a theoretical widening of it. Implication: this is no longer a standing accepted gap. It's tracked in `docs/CHECKLIST.md` as the seed of a future "build the full agent profile" milestone rather than fixed piecemeal here, because the real fix requires deciding what "unknown persona" means once personas are a validated, first-class concept instead of a freely-typed string — the same reason splitting `get_profile`'s fallback was deferred originally, just now with the correct scope of what's actually being deferred.

**Update (docs/decisions/009):** the fix landed there — `get_profile`/`resolve_profile` now fail closed once a `profiles/` directory exists, instead of always falling back to whole-vault access.

Also found and fixed live, not part of the original design: `python -m sympose.cli` never called `load_dotenv()` (unlike `sympose/main.py`), so `VAULT_PATHS` wouldn't reach a bare CLI run at all — harmless while the CLI was pure mock data, a real gap now that grounding depends on it. Fixed in `sympose/cli/__main__.py`.

## Alternatives rejected

- **Building the separate minimal blocking-loop CLI now, alongside wiring the Textual mock.** Rejected for this slice as redundant effort given the Textual mock's live-verified completeness for interactive use — but see Context above: this doesn't resolve ADR 005's scriptable/pipeable-use rationale, which stays open, not dismissed.
- **A single `run_turn` that also streams tokens from the model.** Rejected: `sympose/cli/runtime.py`'s `_stream_reply` already animates a complete reply string word-by-word client-side, so real token-level streaming from the model buys nothing for this slice's only channel and adds real complexity (a generator-shaped engine API, partial-failure handling mid-stream). Revisit if/when a channel genuinely needs true incremental tokens.
- **Writing a meta-only session file at session-open time**, pruned later by a sweep. Rejected in favor of deferring the write until the first turn — it's simpler (no sweep code to write or test) and gets the same "no ghost sessions" outcome as a direct consequence of the write timing.
- **Passing the raw message to `search_structured` unmodified, as originally designed.** Rejected after live verification showed it grounds almost nothing for real chat phrasing (see Context) — replaced with the whole-message-then-per-word fan-out above, discovered and fixed within this same slice rather than shipped and revisited later, given grounding's "non-negotiable" status (`docs/VISION.md`).

**Path update (docs/decisions/011):** sessions no longer live in a top-level `sessions/<handle>/`; they are `profiles/<handle>/sessions/<id>.jsonl`, and `SYMPOSE_SESSIONS_DIR` is gone. With no `profiles/` directory at all they stay in `./sessions/<handle>/`. The session file format described here is unchanged.

**Update (docs/decisions/012):** the placeholder soul is now `DEFAULT_SOUL`, the fallback for a persona with no `profiles/<handle>/soul.md`; a persona's soul is loaded per turn, and the grounding instruction gained rules about ambiguous references, unseen facts, and current limits.

**Update (docs/decisions/014):** the multi-query workaround described here (the raw message, then each significant word as a separate query against the search matcher) is replaced by a dedicated passage retriever in one pass.

**Update (docs/decisions/025):** a turn record now also carries `sent`: the notes (path and heading), recaps (session ids), rewritten search query and count of turns left out that reached the model on that turn. It is for diagnosis and is never read back into a prompt.
