# 007 — litellm for model calls, `ollama_chat/` prefix, local-first default

## Context

The chat engine (`docs/decisions/006`) needs to actually call a language model. No LLM client library exists anywhere in this codebase yet — `pyproject.toml`'s dependencies are `fastapi`, `uvicorn`, `pyyaml`, `python-dotenv`, `textual`. `docs/CODE_QUALITY_STANDARDS.md`'s hard-gate on new dependencies requires weighing at least one lighter alternative, not just asserting the choice made, so that's done explicitly below.

`docs/VISION.md`'s "Lesson from legacy" section is direct about the mistake to not repeat: legacy had real local-model plumbing (`model_router.py` warmed and tracked Ollama models, detected local vs. cloud) but its actual `DEFAULT_CHAT_MODEL` was a hardcoded cloud Gemini model — the infrastructure for "cheap and local" existed but wasn't what a fresh install actually ran. Legacy's failure there was the hardcoded cloud default, not litellm as a library; nothing about litellm itself caused that mistake.

## Decision

**Add `litellm` to `pyproject.toml`'s main `dependencies`** (not `dev` — it ships with the real entry point, same tier as `fastapi`). One call shape, `litellm.completion(model=..., messages=...)`, works uniformly across `ollama_chat/<model>` (local) and any cloud provider Sympose opts into later, with tool-calling-format normalization already built in — which the MCP milestone (on `VISION.md`'s roadmap, not this slice) will need regardless of what calls the model.

**Prefix: `ollama_chat/<model>`, not `ollama/<model>`.** Ollama exposes two different APIs: an older raw-completion endpoint and a newer structured-chat endpoint that takes system/user/assistant messages natively. litellm's `ollama/` prefix targets the former — it hand-assembles a single prompt string from the messages itself, which depends on litellm guessing a template that matches the model. `ollama_chat/` targets the latter — it sends the actual message list and lets Ollama's own chat template apply it, the format Ollama is actually built and tested against for chat. This matters concretely here: grounding depends on the model reliably respecting a system-prompt-injected vault-context block, and `ollama_chat/`'s native role handling is the more dependable path for that than a hand-assembled prompt blob. Clean tool-calling for the later MCP milestone also only works properly through the chat endpoint.

**Default model:** `DEFAULT_LOCAL_MODEL = "ollama_chat/gemma2:9b"` in `sympose/engine/model.py` — `VISION.md`'s own open-question shortlist candidate, confirmed to run comfortably on the dev machine (Apple M2, 24GB RAM). This is the literal fallback a fresh checkout runs with, not an opt-in — the direct fix for the "Lesson from legacy" gap above.

**Override:** a new settings key, `chat_model`, read via `settings_store.get("chat_model", DEFAULT_LOCAL_MODEL)` — same precedent as ADR 003's `active_vault` key in the same store, no new persistence mechanism. `run_turn`'s own `model=` parameter (wired to the CLI's existing `/model` picker) overrides per-call without touching the settings file, so the picker "just works" against the real engine already.

**No new env var for Ollama's connection itself** — litellm already honors `OLLAMA_API_BASE` (default `http://localhost:11434`); documented in `.env.example`, not a new Sympose-owned setting.

**Call shape: non-streaming.** `call_model` calls `litellm.completion(...)` without `stream=True` and extracts `.choices[0].message.content` directly, inside the same `try` that wraps the call — a closer look caught that the extraction originally sat *after* the `try`/`except`, so a 200 response with an empty `choices` list or a null `.content` (a content-filtered or tool-call-only reply) raised a raw `IndexError`/`AttributeError` instead of the `EngineModelError` every other failure path here produces; an empty extracted string is now also treated as a failure, not a silent blank reply. `sympose/cli/runtime.py`'s `_stream_reply` already animates a complete string word-by-word client-side, so token-level streaming from the model isn't needed for this slice's only channel.

**Timeout: 120 seconds, not unbounded.** A closer look caught that `litellm.completion(...)` had no `timeout`, and combined with `docs/decisions/006`'s `app.turn_lock` (one call in flight at a time, held for the call's whole duration), a genuinely hung request — a stalled local Ollama process, a network partition to a cloud endpoint — would wedge every future message behind it forever: no error, no way out short of killing the process, since a thread blocked in a network call can't be cancelled from outside. `_REQUEST_TIMEOUT_SECONDS = 120` in `sympose/engine/model.py` turns that into a recoverable `EngineModelError` instead — generous enough for a genuinely slow local generation to complete under normal conditions (every live turn in this slice finished in single-digit seconds), finite enough that a truly stuck request eventually surfaces rather than hanging indefinitely.

**Cloud model ids in the CLI's picker are real, not placeholders.** `sympose/cli/mock_data.py`'s two cloud `ModelOption`s originally used bare, non-litellm-resolvable ids (e.g. `"claude-sonnet-5"`) as acknowledged placeholders, reasoned to be harmless since cloud wasn't exercised by this slice. A closer look pointed out the actual consequence once the CLI called the real engine: selecting one no longer a no-op, it broke every subsequent chat turn with a confusing connection error until the user manually switched back. Fixed by using real, litellm-resolvable provider-prefixed ids (`anthropic/claude-sonnet-5`, `openai/gpt-4o-mini`) instead — these genuinely work if the matching API key (`ANTHROPIC_API_KEY`/`OPENAI_API_KEY`) is set in `.env`, and fail with litellm's own standard, comprehensible authentication error (still surfaced as a friendly `EngineModelError` line, not a traceback) if it isn't. This makes cloud selection a real, working opt-in for anyone with credentials configured, not just a less-broken placeholder — a small, in-scope correction, not new cloud-credential UX (no onboarding flow, no in-app key entry — still future scope).

## Consequences

One new dependency (litellm) is added, pulling in its own transitive requirements (HTTP client, provider SDKs it lazily imports). `call_model` wraps connection failures, timeouts, and model-not-found errors into a single `EngineModelError` with a user-facing message, so a stopped-Ollama, hung-request, or wrong-model-name case each surface as a friendly in-transcript error in the CLI rather than a raw traceback or an indefinite hang. Switching `chat_model` to a cloud provider needs no code change, only the corresponding API key in `.env` — litellm resolves provider credentials the same way regardless of which provider string is used, and the CLI's own `/model` picker now offers two real (not placeholder) cloud options that work under exactly that condition.

## Alternatives rejected

- **stdlib `urllib.request` calling Ollama's `/api/chat` HTTP endpoint directly, zero new dependencies.** A real, close alternative for this slice specifically — it's Ollama-only and this slice only exercises Ollama. Rejected because it defers, rather than avoids, the actual cost: the moment cloud opt-in or MCP tool-calling lands (both already on the roadmap, not hypothetical), a hand-rolled client would need to grow its own provider-format normalization and tool-calling-schema translation — work litellm already does. Paying the one-dependency cost now, for a library that already covers where this is headed, was judged better than writing a second bespoke client later. Revisit if litellm's transitive footprint turns out heavier than expected in practice.
- **`ollama/<model>`, matching what a first web search for "litellm ollama" often shows.** Rejected per the `ollama_chat/` reasoning above — it's the less reliable choice for exactly the two things this engine needs most (system-prompt-following for grounding, and clean tool-calling later).
- **Porting legacy's `model_router.py` local/cloud heuristic routing (`is_simple_message`, Ollama warm-detection via `/api/ps`, background warm-up) in this slice.** Rejected as scope beyond what v0 needs — one configured local default with a manual override already delivers "local-first by default, cloud reachable," which is the actual principle at stake. The warm/simple-message routing is a cost-optimization refinement on top of a working default, not a prerequisite for having one; revisit as its own later slice if real usage shows it's worth the added complexity.
