# 010 — Persona-scoped nebula graph, model precedence, and a default-persona setter

## Context

ADR 009 gave `profile.py` its final shape and deliberately left three things open, each with no consumer at the time: nothing writes the `default_persona` setting, a profile's `model` field is display-only, and the Knowledge Nebula's `GET /api/vault/graph` takes no persona at all. The graph route was whole-vault by design ("the nebula is an explorer surface, not a persona-scoped one"), which means it currently exposes the titles, tags, folder names, and link structure of notes a restricted persona (one whose `vault_folders` excludes them) can never read. Every other persona-aware route already scopes to the persona's `vault_folders`, the dashboard already keeps an active persona and sends it to `GET /api/vault/tree`, and a graph is only useful if it reflects what the active persona can actually work with. This record closes all three together because they are the same kind of change: making a field on the profile do what it says.

## Decision

**Persona-scoped graph.** `GET /api/vault/graph` takes an optional `persona` query parameter and resolves it through `require_profile`, exactly like `GET /api/vault/tree`. The manifest is built from only the notes the persona can see (the same scoped snapshot the tree route uses), so a bare `[[Name]]` resolves among visible notes and node size (`val`, link degree) counts only visible links. A scoped build has exactly one flaw: a link from a visible note to a *hidden* one is unresolved, so it would become a ghost node named after the hidden note, leaking the title this change exists to hide. To close that, any ghost whose name matches a note that exists anywhere in the vault (checked against the whole-vault snapshot, which is mtime-cached) is dropped along with its links; the ghosts that remain are genuinely broken links. An unrestricted persona (`vault_folders: '*'`) skips that extra check, so the default persona's graph is unchanged. The dashboard passes its active persona and refetches when it changes.

**Model precedence.** A profile's `model` now takes part in resolution: an explicit per-call model (the CLI's `/model` pick) beats the persona's `model`, which beats the `chat_model` setting, which beats the built-in local default. `engine/model.py`'s `resolve_model` gains an optional `persona_model` argument and remains the single place this order is defined below the explicit pick; `run_turn` calls it rather than inlining the persona step, and the dashboard's roster route and the CLI's header both display `resolve_model(...)` instead of re-deriving it, so what is shown is what runs. The CLI stops preselecting the first entry of its model list: it starts with no explicit choice (so a persona's own model, or the setting, actually applies) and only records one once the user picks from `/model`. A picked model still sticks across persona switches, as before. `skills` stays display-only; it is not part of this decision.

**Default-persona setter.** `profile.set_default_persona(handle)` validates the handle against the roster (`list_profiles()`, so it cannot store an unknown or unsafe handle, which would make `resolve_profile` fail closed for every unqualified request), lowercases it (nothing else normalizes case on write, which was the latent mixed-case gap ADR 009's review found), and writes it through `settings_store`. The CLI gets a `/default` command that makes the currently selected persona the default. No dashboard control is built here; the function is the seam for one.

## Consequences

The nebula for a restricted persona shows fewer nodes and a smaller graph than the whole vault, which is the intended behavior, not a regression. The persona-independent nebula described in the frontend's `use-nebula-graph.ts` doc comment and the wiki's Module A no longer holds and those comments are updated. Any consumer that calls the graph route without a `persona` gets the configured default persona's view, which for the shipped default (Samantha, whole vault) is unchanged. Switching persona in the dashboard now triggers a graph refetch, one extra request per switch. The manifest's `folders` and `meta` fields stay as they are for future grounding use; this record does not touch them. `TurnResult.grounding` also stays. The tree route builds its manifest from the scoped snapshot too, so the ghost-node behavior described above may exist there; that is outside this record and tracked separately. A persona whose allowed folders hold no notes gets an empty nebula: the dashboard now treats any successful graph response, empty or not, as the live answer, and shows the bundled sample only when the backend is unreachable or answers with an unexpected shape. The same change means a vault with no notes yet (or no vault configured) also shows an empty nebula instead of the sample; the sample's mock notes and tags don't exist in the user's vault and would also feed the editor's `#tag` autocomplete.

## Alternatives rejected

- **Leaving the graph whole-vault**, on the grounds that it is the owner's own explorer view. Rejected: a graph that shows notes the active persona cannot use is not practical data for that persona, and it was the only persona-aware surface that ignored scope.
- **Filtering the whole-vault manifest down to the persona's folders** (the first implementation). Rejected after review: links are resolved against the whole vault before filtering, so a same-named note in a hidden folder can capture a link that should resolve to a visible note, and the visible edge is then dropped. Building from the scoped snapshot resolves among visible notes; the ghost-name leak it introduces is handled by the targeted ghost check above.
- **Building from the scoped snapshot with no ghost handling.** Rejected for the title leak described above.
- **Persona model always winning over an explicit `/model` pick.** Rejected: an explicit, in-the-moment choice by the user should beat configuration.
- **A hardcoded model literal per persona in the CLI's list.** Rejected: `resolve_model` already owns the order, and duplicating it would let display and behavior drift.
- **A `--default` flag or picker submenu instead of a `/default` command.** Rejected as heavier than a one-word command acting on the persona already selected.
