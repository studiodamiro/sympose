# Sympose Engineering Log: Stylo 0.13.0 → 0.13.1 — Preview Scroll Container + `readOnly` Now Actually Blocks Editing

> **Date:** Sunday, September 13, 2026
> **Topic:** stylo shipped 0.13.1 same-day, closing two more gaps the
> read/edit toggle's own animation work surfaced: `preview` had no scroll
> container at all (long notes clipped, no scrollbar), and in-place
> `readOnly` never actually stopped the right-click menu or floating
> selection bar from dispatching real edits. Filed as
> `stylo/docs/requests/2026-09-13_preview-missing-scroll-container.md` and
> `2026-09-13_readonly-ignored-by-context-menu-and-selection-bar.md`;
> both shipped together in 0.13.1.
> **Participants:** damiro (Lead Architect), Grace (Engineering Partner)
> **Status:** `npm run typecheck` clean, `npm run build` rebuilt
> `sympose/webui/`. No Python touched, so `.venv/bin/pytest` wasn't
> re-run for this bump specifically.

## What shipped

`ui/package.json` `@damiro/stylo` `^0.13.0` → `^0.13.1`.

### Preview scroll container

`.preview` (`stylo.module.css`) was the one surface missing the
`flex: 1 1 auto; min-height: 0; overflow: auto` pattern `.source` and
`.inplace` already had — a note longer than the visible panel just got
clipped by `.root`'s `overflow: hidden`, no scrollbar reachable. 0.13.1
brings `.preview` in line with the other two surfaces.

This gap also explained a second bug fixed on Sympose's own side the
same day: the vault-browsing slide animation (`use-slide-swap.ts`) only
ever scoped to `.cm-scroller` (CodeMirror's scroll viewport, absent in
`preview`) and `.sy-note-footer` — switching notes while read-only had
no matching descendant to animate at all, so it either snapped instantly
or got stuck mid-transition depending on whether the note had outbound
links. Fixed by wrapping the read-mode breadcrumb + rendered body in a
new `.sy-note-preview` class and adding it as a third scoped target
alongside the existing two.

### `readOnly` now blocks the context menu and selection bar

Traced the actual dispatch path rather than trusting the prop name:
`EditorState.readOnly` only gates DOM-originated input (keyboard/paste/
IME) — it never blocked a plain `view.dispatch(...)` call from
elsewhere in the extension stack, and neither `menu-plugin.ts` nor
`selection-bar.ts` checked `readOnly` at all before running a command.
Both now check `view.state.readOnly` — the context menu falls back to
the browser's own (same as `contextMenu: false` today) and the
selection bar doesn't appear.

Sympose doesn't use in-place `readOnly` today (the read/edit toggle
uses `mode="preview"` specifically because of this gap — see
`markdown-panel.tsx`'s file doc comment), so this has no functional
effect on Sympose's own behavior. Landed anyway because the investigation
that found it is now a permanent citation in that same doc comment, and
because a `readOnly` prop that doesn't actually block editing everywhere
is a real correctness gap for any future consumer.

### Verified in the installed package

- `node_modules/@damiro/stylo/dist/styles.css` — `._preview_*` rule now
  includes `min-height:0; ... flex:auto; ... overflow:auto`.
- `node_modules/@damiro/stylo/dist/InPlaceView-*.js` now references
  `state.readOnly` (previously absent from that chunk entirely).
