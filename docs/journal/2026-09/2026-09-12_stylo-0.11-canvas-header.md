# Sympose Engineering Log: Stylo 0.10.1 → 0.11.0 — Frontmatter Card Moved onto `canvasHeader`

> **Date:** Saturday, September 12, 2026
> **Topic:** stylo (`@damiro/stylo`, ADR-080) shipped 0.11.0 the same day, adding
> `canvasHeader` — a seam purpose-built (its own docs example uses
> `<FrontmatterCard>`) for exactly the placement problem sympose's frontmatter
> card had been working around since ADR-080: `toolbar.render` can wrap
> content *before* the whole editing surface, but can't land it *inside* the
> canvas, under CodeMirror's own find/replace panel and above the document
> body. Bumped the install and moved the card onto the real seam.
> **Participants:** damiro (Lead Architect), Grace (Engineering Partner)
> **Status:** `npm run typecheck` clean, `npm run build` rebuilt
> `sympose/webui/`, `.venv/bin/pytest` 367 passing (no Python touched).

## What shipped

### Version bump

`ui/package.json` `@damiro/stylo` `^0.10.1` → `^0.11.0`. The gap is one
release (0.11.0 itself); its CHANGELOG lists `canvasHeader` under `Added`,
plus two `Fixed` entries (a caret-past-table edge case, an embed click-drift
bug) and one `Changed` (toolbar wraps by group). None marked `BREAKING`.

### Frontmatter card: `toolbar.render` → `canvasHeader`

[markdown-panel.tsx](../../../ui/src/components/sympose/markdown-panel.tsx)
previously rendered `<FrontmatterCard>` from inside `toolbar.render`, riding
below the toolbar row purely because no better seam existed — the code
comment at the time said so outright. `canvasHeader` (stylo `>=0.11.0`) is
that seam: it docks host content under CodeMirror's own find/replace panel
and above the document body, built on the same `showPanel` mechanism as the
search panel itself, so it's part of the same coordinate system rather than
a separately positioned overlay.

Moved the card there. Two things had to change shape to fit stylo's
contract:

- **`canvasHeader` is read once, at mount** — same rule as `inPlace` and
  `wikiLinkSource`. `frontmatter`/`onWikiLinkClick`/`phone` all can change
  without a remount (a note's frontmatter loads async after `<Stylo>` mounts;
  `phone` flips on a viewport breakpoint), so the function handed to `<Stylo>`
  reads them off a ref (`frontmatterCardStateRef`, kept current every render)
  inside a `React.useCallback(() => …, [])` — the same ref-plus-stable-
  callback pattern `wikiLinkSource` already established in
  [app-shell.tsx](../../../ui/src/routes/app-shell.tsx) for the identical
  reason.
- **`toolbar.render` lost the frontmatter block entirely** — it now only
  wraps the note-actions `⋯` menu over stylo's own toolbar row, which was
  already `toolbar.render`'s sole legitimate job once ADR-080's original
  placement compromise no longer had to double as the card's home too.

### Verified against a real note, not a mock

Ran a scratch Playwright + Chromium pass — a throwaway `python3 app.py
--dashboard` backend pointed at an isolated scratch vault (`MASTER_VAULT_PATH`
override) rather than the real `garden` vault, and a throwaway `vite` on a
second port (`SYMPOSE_API_URL` pointed at the scratch backend) rather than
touching the shared `:5173` dev server. A note with a real `---` frontmatter
block and ~100 lines of body confirmed all three of `canvasHeader`'s
documented guarantees hold in sympose's actual wiring, not just in stylo's
own docs:

1. The card renders as a genuine child of `.cm-panels.cm-panels-top` inside
   `.cm-editor` — not a sibling element positioned to look right.
2. Scrolling the document (`.cm-scroller.scrollTop`) leaves the card pinned
   in place — only the body moves underneath it.
3. Opening find/replace (`Cmd-F`) inserts its panel *above* the card, which
   stays put below it — matching the documented stacking order exactly.

Scratch backend and vite instance killed after the check; nothing checked
into either repo. damiro's own shared `:5173`/dashboard processes were left
untouched throughout.

**A near-miss worth recording:** the first attempt at this check ran
straight against the shared dev server, which was pointed at the real
`garden` vault. A text-based Playwright locator (`getByText("Add remove
event lis...")`, matched against a vault-tree row from an unrelated earlier
listing) actually resolved to a stale element in an open chat transcript by
the time the click landed, and a `force: true` click meant to get past a
transitional overlay hit a thumbs-up feedback control on a real historical
message instead of opening a note. Confirmed via `git status`/`stat` in
`garden` that nothing was written — the note path referenced in that
transcript's "Note saved" chip predated the click by two weeks — but the
click itself was a real, unintended interaction with production chat state.
The fix wasn't a more careful locator; it was routing the whole check through
an isolated scratch vault + scratch backend before any clicking started, so
a bad selector can only ever land on throwaway data. Doing that from the
first attempt, not the second, is the standing lesson.

## Follow-up in the same session: find/replace panel cleanup

Moving the frontmatter card onto `canvasHeader` put it directly under
CodeMirror's own find/replace panel for the first time, which surfaced two
things worth fixing while both were on screen together in
[index.css](../../../ui/src/index.css):

- **The find/replace panel didn't read as the same surface as the main
  toolbar** — different height, and its buttons/fields never matched
  `.toolbarButton`'s own metrics (28px tall, `calc(var(--stylo-radius) -
  3px)` radius). Both are already token-driven (`--stylo-*`) per stylo's
  `theme.ts`, so the mismatch was sizing, not missing theme wiring.
- **A stray hairline sat under the frontmatter card** — not stylo's doing:
  `@codemirror/view`'s own `baseTheme` hardcodes `&light .cm-panels-top {
  border-bottom: 1px solid #ddd }`, untouched by stylo's `--stylo-*` dark
  palette, so it always renders on Sympose's dark surface regardless of
  theme.

Fixed both, plus restored the open/close slide animation that a prior
session's fix had (correctly, at the time) traded away:

- `--h` (the CSS variable stylo's own slide keyframes target) bumped from
  its 32px default to 36px — the main toolbar's own total row height (28px
  `.toolbarButton` + 4px top/bottom padding, from stylo's
  `stylo.module.css`) — plus matching `height: 28px`/`box-sizing:
  border-box` on `.stylo-search-field`/`.stylo-search-button` so the row's
  controls are the same size as toolbar buttons, not just the same colors.
- `[data-slot="markdown-panel"] .cm-panels.cm-panels-top { border-bottom:
  none !important; }` removes the CodeMirror baseTheme line.
- The slide animation: a prior fix set `height: auto !important` on the
  panel to stop a wrapped (narrow-width) row from being permanently clipped
  at stylo's fixed single-row height — but `!important` on a normal-origin
  author rule outranks a running CSS *animation* in the cascade regardless
  of specificity, which is what silently killed the slide entirely (stylo's
  own open/close keyframes were still attached and firing, just always
  overridden mid-flight). Dropping `!important` from that one declaration
  — keeping only higher *selector* specificity to still win the *resting*
  state after stylo's own less-specific `height: var(--h)` rule — lets the
  cascade order do the right thing in both cases: the CSS Animation origin
  (which always beats normal-origin author rules, `!important` or not)
  drives `height` while the slide is actually playing, then control passes
  to this rule's plain `auto` once the animation ends, sized correctly for
  either a single toolbar-height row or a wrapped multi-row narrow-width
  case. Verified both directions (open via `Cmd-F`, close via the panel's
  own `×` button) with a scratch Playwright pass capturing mid-animation
  frames, again against the isolated scratch vault/backend rather than the
  shared dev server.

## Second follow-up, same session: search-row sizing and frost transparency

Two more things surfaced once the search panel and frontmatter card were
actually sitting stacked together in the browser rather than reasoned about
from source:

- **Matching the search buttons' font-size to `.toolbarButton`'s own
  0.75rem made the row heavier, not lighter.** The toolbar's buttons are
  icons; the search row's are words ("next", "previous", "replace all"), so
  the same font-size read as visually larger text next to small glyphs, and
  the extra width pushed the row into wrapping a second line more often
  than before — taller than the toolbar it was meant to match, the opposite
  of the goal. Dropped the button font back to 0.6875rem (stylo's own
  original), buttons' horizontal padding `0 8px` → `0 6px`, and
  `.stylo-search-check` (the match-case/regexp/by-word labels, previously
  unstyled by this file) down to 0.625rem — confirmed via a scratch
  Playwright pass that a find/replace panel which previously wrapped its
  buttons onto a second row now fits find/next/previous/all/replace/replace
  all on one line even in a ~470px editor column, leaving only the three
  checkboxes to wrap onto their own (much shorter) second line in that
  narrow case — a real improvement, not just a smaller version of the same
  problem.
- **The frontmatter card was never part of the nebula-frost transparency
  system at all, and used the wrong base color even at rest.** It painted
  `bg-background` (Tailwind's `--background`, the app's darkest base canvas
  tone) instead of `bg-panel` (`--panel`, the "raised working surface" the
  toolbar and editor use via `--stylo-bg`) — two genuinely different
  shades, so it always read as a mismatched, more opaque block sitting on
  the editor surface, frost or no frost. Fixed by switching to `bg-panel`
  in [frontmatter-card.tsx](../../../ui/src/components/sympose/frontmatter-card.tsx)
  and giving its root a `data-slot="frontmatter-card"` — the same
  addressing convention every other override in this file already uses —
  then adding both that and `.cm-panels.cm-panels-top` (the find/replace
  panel's own background layer, separate from `.stylo`'s, the same reason
  `.cm-editor` and the toolbar each needed their own entry originally) to
  the existing `[data-nebula-frost="tint"]` transparent-drop rule. Verified
  by forcing `data-nebula-frost="tint"` directly in a scratch page (no need
  to walk the real Settings UI for a CSS check) and reading back
  `getComputedStyle(...).backgroundColor` on all four surfaces — toolbar,
  `.stylo` root, the find/replace panel, and the frontmatter card all came
  back `rgba(0, 0, 0, 0)` together.

## Third follow-up, same session: Replace field radius, frontmatter card tint, and a stylo request

Rounded the Replace field's corners — stylo squares them deliberately
(`theme.ts`, so the field reads as attached to the Replace/Replace-all
buttons via its own `border-left` divider), but next to the Find field's
rounded ones it just looked like an unstyled default rather than a
deliberate group edge. Overrode `border-radius` back to the shared field
formula; the `border-left` divider alone already carries the grouping.

**A correction to the previous entry's frost-transparency fix:** dropping
the frontmatter card fully transparent under Knowledge Nebula frost (the
same binary treatment as the toolbar/editor/search panel) was wrong once
seen live — those three are full-width bars that don't need their own
background to read as separate regions; the frontmatter card is an inset,
rounded card, and going fully clear left only its outline with nothing
inside it, indistinguishable from a rendering bug. Fixed by giving it
`.sy-frosted-panel` directly (`frontmatter-card.tsx`) — the same
opacity-aware `color-mix` fill `<MarkdownPanel>`'s own outer card already
uses — instead of a flat `bg-panel`/`bg-background`, and removed it from
the binary transparent-drop list in index.css. It now keeps a dimmed tint
under frost rather than vanishing, confirmed by reading
`getComputedStyle(...).backgroundColor` before/after: the toolbar and
search panel land on `rgba(0, 0, 0, 0)`, the frontmatter card lands on a
real (dimmed) color.

**Two more asks — icons on the search panel's next/previous/all/replace/
replace-all buttons, and one-word checkbox labels (case/regex/word instead
of match case/regexp/by word) — turned out to need a stylo change, not a
Sympose one.** Traced `search-panel-dom.ts`: every button is built with
`el.textContent = label` (a plain text node, not a slot), and every label —
button and checkbox alike — comes from `view.state.phrase(...)`, CodeMirror's
own i18n lookup, which `<Stylo>` doesn't expose an `extensions` (or
`phrases`) passthrough for a host to override, even though the underlying
CodeMirror mechanism is genuinely host-configurable in principle. A
`MutationObserver` DOM-patching workaround was considered and ruled out —
the same "reaching into undocumented internals" cost the 0.9.0 upgrade audit
already flagged elsewhere, except mutating live DOM stylo itself owns and
re-renders rather than just reading computed geometry. Wrote up
[`2026-09-12_search-panel-icons-and-short-labels.md`](../../../../stylo/docs/requests/2026-09-12_search-panel-icons-and-short-labels.md)
in stylo's own `docs/requests/` (the same convention behind today's earlier
`canvasHeader` request) proposing a `searchPanel.{icons,labels}` prop
shaped like the main toolbar's existing `icons` prop — not implemented here,
per the standing rule that stylo is a fixed external dependency from
Sympose's side.

## Fourth follow-up, same session: the frost-tint fix didn't actually read as a color

The previous entry's `.sy-frosted-panel` swap for the frontmatter card was
still wrong, seen live a second time: `.sy-frosted-panel` at the default
(frost off) opacity renders *exactly* `--panel` — byte-identical to what
`--stylo-bg` already paints the toolbar and canvas with — so the card
matched its surroundings so precisely it read as having no color of its
own at all, same complaint as two revisions ago for a different reason.
Chasing the Knowledge Nebula opacity dial was the wrong idea twice in a
row: this is a small inset card, not the editing surface itself, and it
needs to reliably look like a raised card regardless of where that dial
sits, not fade in and out with it. Settled on `bg-muted` instead —
`--muted`/`--accent` (0.274 lightness in dark mode) one genuine, fixed
step above `--panel` (0.21) — unconditionally, no frost logic at all.
Confirmed via computed style: toolbar `oklch(0.21 0.006 285.885)`,
frontmatter card `oklch(0.274 0.006 286.033)` — a real, visible difference
this time, not a coincidental match.

Two more fixes from the same live look: the close (`×`) button's
`margin-left: auto` (stylo's own rule, meant to pin it to the panel's far
right edge) collapses to zero gap the instant the row is tight on space —
exactly the wrapped-checkboxes case this whole thread keeps landing in —
butting it straight against "by word" with nothing between them. Swapped
for a fixed `margin-left: 12px`, trading "pinned to the far edge in the
roomy case" for "never collapses to zero" — confirmed a 16px gap via
`getBoundingClientRect()` in the wrapped state. And the button/field/
checkbox fonts, having already been stepped down twice this session, still
read as too large next to the icon-only toolbar above — dropped once more:
fields 0.75rem → 0.6875rem, buttons 0.6875rem → 0.625rem, checkboxes
0.625rem → 0.5625rem. At this size the whole row — find, next, previous,
all, replace, replace all, all three checkboxes, and the close button —
now fits on one line even at the same ~470px editor-column width that
forced a two-row wrap in every earlier pass this session.

## Fifth follow-up, same session: two stylo requests, and the frontmatter card gets a real transparency knob

Two more asks from the same live look at the search panel — icons on
next/previous/all/replace/replace-all, and one-word checkbox labels
(case/regex/word) — turned out to need a stylo change on inspection, not a
Sympose one, same as the checkbox-group-wrap question below. Traced
`search-panel-dom.ts`: every button is built with `el.textContent = label`
(a plain text node, not a slot), and every label comes from
`view.state.phrase(...)`, CodeMirror's own i18n lookup — genuinely
host-configurable in CodeMirror core via `EditorState.phrases.of(...)`, but
`<Stylo>` doesn't expose an `extensions` (or `phrases`) passthrough for a
host to supply one; grepped `Stylo.tsx`/`types.ts` for `extensions`,
`phrase`, `i18n`, `labels` — none exist. A `MutationObserver` DOM-patching
workaround was considered and ruled out — the same "reaching into
undocumented internals" cost the 0.9.0 upgrade audit already flagged
elsewhere, except mutating live DOM stylo itself owns and re-renders.
Wrote up
[`2026-09-12_search-panel-icons-and-short-labels.md`](../../../../stylo/docs/requests/2026-09-12_search-panel-icons-and-short-labels.md)
proposing a `searchPanel.{icons,labels}` prop shaped like the main
toolbar's existing `icons` prop.

**Checkbox group-wrap turned out to be the same class of problem.** Asked
whether the three option checkboxes could wrap as one unit instead of
splitting mid-group across the wrap boundary — traced it to the same flat
DOM `buildSearchDom` builds (eleven siblings, no group wrapper around the
checkboxes), and the same fix already tried and reverted earlier this
session (`flex-basis: 100%` on the first checkbox) pushes the *other two*
onto a third line instead of joining the second — worse, not better.
Atomic group-wrap needs an actual nesting boundary flexbox can wrap as one
item, which means `search-panel-dom.ts` nesting the three checkboxes in
their own container div — a DOM change, so filed as its own request,
[`2026-09-12_search-panel-checkbox-group-wrap.md`](../../../../stylo/docs/requests/2026-09-12_search-panel-checkbox-group-wrap.md),
rather than folded into the icons/labels doc (different concern, same
file, kept separate per the one-topic-per-request convention the
`canvasHeader` doc set).

**The frontmatter card's color, take three.** The `.sy-frosted-panel` fix
from two entries ago was *still* wrong: it fills from `--panel` at the
Knowledge Nebula opacity knob's default (1) — byte-identical to
`--stylo-bg`, so the card matched its surroundings exactly and read as
having no color at all, again. damiro also flagged that `<Card>`'s own
`bg-card` would hit the identical wall (`--card` and `--panel` are the
same oklch value in dark mode) before asking for it directly, which
confirmed reusing either token here was the wrong move regardless of which
one. Settled it by building a sibling to `.sy-frosted-panel` —
`.sy-frontmatter-panel`, same `color-mix` formula against
`--sy-panel-opacity`, but from `--muted` (one genuine step lighter) rather
than `--panel` — so the card is visibly distinct from the toolbar/canvas
at the knob's default *and* still answers the same knob, fading
proportionally with everything else instead of being the one surface that
ignores it. Verified via computed style through an actual cookie-driven
reload (`document.cookie = "sympose:nebula.panel_opacity=0.4"`, matching
how the real Settings slider persists it): at opacity 1 the card resolves
to a distinct opaque color from the toolbar's `--panel`; at 0.4 the same
base color carries a `/ 0.4` alpha, while the toolbar (still on the binary
`.stylo`/`.cm-editor`/toolbar/search-panel drop) goes fully `rgba(0,0,0,0)`
— both fading, from different starting points, exactly as intended.

Also updated
[`docs/wiki/reference/ui-design-reference.md`](../../wiki/reference/ui-design-reference.md)
§3.4 with the general lesson, since this is the third time a "raised
surface" color choice collided with a working surface's own background
this session: `--panel` and `<Card>`'s `--card` coincide in dark mode, so
defaulting to `--card` for any component that might end up nested inside
an already-`--panel` surface is a real trap, not a hypothetical one — and
any new raised surface added inside the editor should hook into the shared
panel-opacity knob rather than staying permanently opaque while its
neighbors fade.

## Sixth follow-up, same session: unifying `<StyloToolbarSettings>` with the frontmatter card

A direct question — "why does the toolbar-button customizer's card look
different from the frontmatter card?" — traced to two entirely separate
components, not two flavors of the same card: `<StyloToolbarSettings>`
(Settings > Markdown editor > Toolbar buttons) is stylo's own component,
scoped in `index.css` via `[data-slot="toolbar-settings"] { --stylo-bg:
var(--background), ... }` — deliberately the page's darkest tone, since it
sits directly on the bare Settings page with no wrapping card of its own
and was built to read as a *recessed* content area. The frontmatter card
sits *inside* an already-`--panel` editor surface and needs the opposite —
`--muted`, one step *lighter* — to read as *raised* against it. Consistent
by design, but confirmed as a real inconsistency once seen side by side:
asked to unify them, so `[data-slot="toolbar-settings"]`'s `--stylo-bg`
moved from `--background` to `--muted`, matching the frontmatter card's own
fill. No panel-opacity knob wired in here (unlike the editor's frosted
surfaces) — Settings has no ambient nebula behind it for a fade to reveal.
Also caught and fixed a comment in the same block that had gone stale
mid-session: it still credited `<FrontmatterCard>` with the old
`--background` choice, from before this thread moved it through `bg-panel`
→ `.sy-frosted-panel` → `.sy-frontmatter-panel`.

**Font sizes matched to the search panel's own buttons while in there.**
`<StyloToolbarSettings>`'s CSS module sets font-size directly on its
command-label spans (0.8125rem) and "Add"/"×" text buttons (0.75rem) —
no `--stylo-font-*` token reads, unlike the CodeMirror-side theme, so the
`--stylo-*` scope couldn't reach them either. Targeted structurally
(`[data-slot="toolbar-settings"] li span` / `li button`) rather than by the
module's own hashed class names (`_label_18hcd_121`, confirmed via
Playwright DOM inspection) — those hashes are stable within one stylo
build but re-hash on every version bump, the same brittle-coupling risk
this file avoids everywhere else. Both now render at 0.625rem, matching
`.stylo-search-button` — one consistent scale across both of stylo's
text-button surfaces in the app instead of three different sizes doing the
same job (search buttons, toolbar-settings labels, toolbar-settings "Add").

Hit real Playwright flakiness verifying this one — `ControlSection`'s
collapse-state triggers weren't reliably clickable by visible text alone
(a `getByText` click sometimes silently toggled the wrong ancestor, or hit
a still-animating trigger). Settled on querying `[aria-expanded]` directly
and clicking via `getByRole("button", { name })` instead of guessing at
text-node ancestors — worth remembering for the next scratch-vault check
in this app's Settings panel specifically.

## Seventh follow-up, same session: "Add" becomes a `+` to match "Remove"'s `✕`

Asked to swap the "Available" column's "Add" text button for a plain `+`
icon, matching "On the bar"'s "Remove" (already icon-only — a bare `✕` in
a 22×22px square). Traced `StyloToolbarSettings.tsx`: both buttons are
built inline in the component itself (not delegated through any prop), and
the `icons` prop only overrides a *command*'s glyph (Bold, Italic, …), not
either action button — so there's no host-facing hook for this one, same
as the other stylo-internals gaps found today, but this one didn't need a
request doc: a pure CSS content-swap covers it without touching any DOM
stylo owns. Collapsed the button's visible text to zero (`font-size: 0`)
and painted a `+` via `::before` sized to the same 22×22px footprint as
"Remove" — the accessible name is untouched since it already comes from
the button's own `aria-label="Add {label} to the bar"`, not its text
content, so nothing changed for a screen reader. Targeted by the
"Available" section's position (`<StyloToolbarSettings>` always renders
"On the bar" first) since both action buttons share the same CSS-module
shape otherwise. Verified functionally, not just visually — clicked the
new `+` in a scratch Playwright pass and confirmed the item count on "On
the bar" actually increased (15 → 16), not just that it *looked* like a
button.

## Eighth follow-up, same session: fenced-code caret-reveal — already shipped, not a gap

Asked to add a Settings option for fenced-code (```` ``` ````) markers to
reveal on caret vs stay hidden — the same caret/never split ADR-007 already
gives every other in-place construct. Before writing anything, traced
whether it already existed: `reveal` (`EditorReveal = "caret" | "never"`,
[use-editor-preferences.ts](../../../ui/src/lib/use-editor-preferences.ts))
already threads straight through to stylo's `inPlace.reveal` in
[markdown-panel.tsx:524](../../../ui/src/components/sympose/markdown-panel.tsx#L524),
surfaced as Settings > Markdown editor > Formatting marks ("Near cursor" /
"Always hidden") since before this session.

The real question was whether that setting reaches fenced code blocks the
same way it reaches headings/emphasis/lists — from the app it looked like
``` fences only had two states (always shown in Plain text mode, always
hidden in Seamless) rather than a caret-aware third state. Read stylo's
actual source rather than the minified dist: `decorateCode` in stylo's own
`src/inplace/nodes-blocks.ts` (not sympose's to edit — traced, not touched),
whose comment cites ADR-007 directly. Under `reveal: "caret"` the block's
`revealed` set already equals the caret-touched-line set, so the ``` fence
lines reveal (`.cm-inplace-fence`, muted-color text) whenever the caret sits
anywhere inside the block — fence lines or content lines alike — and collapse
(`.cm-inplace-code-pad`, zero height) once it leaves. Same mechanism as
every other construct, just gated on the whole block span (open fence →
last content line → close fence) instead of one line; a body-less block
(` ``` ` immediately followed by ` ``` `) keeps a caret-reveal escape hatch
even under `reveal: "never"`, since there's no content line inside it to
land on otherwise.

No sympose or stylo change made — damiro confirmed live, against the
running `:5173` dev server, that a fenced block's ``` already reveal under
caret with Formatting marks set to Near cursor and stay hidden set to
Always hidden. The feature asked for was already fully wired through the
existing `reveal` preference; this entry exists so the next time this looks
like a gap, the trace doesn't have to happen twice.
