# Sympose Engineering Log: Stylo 0.4.0 → 0.9.0 — Upgrade Audit, Dead-Workaround Removal, Wikilink Autocomplete

> **Date:** Friday, September 11, 2026
> **Topic:** stylo (`@damiro/stylo`, ADR-080) shipped five minor versions
> (0.5.0–0.9.0) since sympose adopted it at 0.4.0. Audited the full CHANGELOG
> against what sympose actually has wired, bumped the install, removed
> workarounds two new public tokens made obsolete, verified with a scratch
> Playwright pass against the real dev server, and wired the first of the two
> ADR-080 follow-up gaps: `[[wikilink]]` autocomplete. Also: a comparison
> against known alternatives (§3), a re-audit of the 2026-09-10 integration
> entry's own follow-up list (one item turned out to already be resolved
> upstream, two are still open and higher-priority than anything found in
> this pass), and a features/configuration surface audit (§5) — what stylo
> ships that sympose doesn't wire yet.
> **Participants:** damiro (Lead Architect), Grace (Engineering Partner)
> **Status:** `npm run typecheck` clean, `npm run build` rebuilt
> `sympose/webui/`, `.venv/bin/pytest` 367 passing (no Python touched).

## 1. What shipped

### Version bump

`ui/package.json` `@damiro/stylo` `^0.4.0` → `^0.9.0`. Read stylo's own
CHANGELOG end to end: every version in the gap (0.5.0–0.9.0) is `Added` /
`Changed` / `Fixed`, none marked `BREAKING` — the only breaking change in
stylo's history (the CodeMirror peer-dependency move) is 0.2.0, already inside
what sympose had. `npm install` pulled `@codemirror/autocomplete` and
`@codemirror/search` as stylo's own regular (not peer) dependencies, deduped
to the single CodeMirror instance already in `ui/node_modules` — no new peer
install needed on sympose's side.

### A real live bug, fixed by the bump alone

Settings › Markdown editor exposes `reveal: "caret" | "never"` as a shipped
preference (`use-editor-preferences.ts`). On 0.4.0, choosing "never" ("always
hidden") did not actually hide everything its name promised: a fenced code
block's fences, a `---` thematic break, and inline/one-line `$…$` math all
still revealed their raw source the moment the caret entered them, regardless
of the setting. Stylo 0.9.0 closes all three gaps natively (right-click
**Language** / **Remove code block**, Backspace/Delete/right-click **Remove
divider**, and a right-click **Math** field respectively). No sympose code
change was needed — the bump alone fixes a preference that was silently
half-working.

### Two workarounds retired by new public tokens

- **`--stylo-font-size`** (stylo 0.5.0) replaces the `!important` reach into
  `.cm-editor` sympose had been carrying since adoption
  ([index.css](../../../ui/src/index.css), now folded into the `.stylo` token
  block at `--stylo-font-size: 0.875rem`).
- **`--stylo-font-family`** (stylo 0.6.0) replaces the `!important` reach into
  `.cm-content` for body prose (`--stylo-font-family: var(--font-sans)`). The
  heading override (`--font-heading` on `.cm-inplace-h1`–`h6`) stays as its
  own `!important` rule — no per-construct token exists for splitting heading
  font from body font, so that one rule is still doing real work, not
  duplicating a token.

Both are token assignments now, not fights against CodeMirror's injected
`EditorView.theme()` stylesheet. Confirmed visually and via computed style
(`getComputedStyle` on `.cm-editor`/`.cm-content` in a scratch Playwright
pass) — `font-size: 14px`, `font-family: "Inter Variable", sans-serif` on
body, headings still serif.

### Dead code removed, verified before deleting

The selection-bar-vs-context-menu overlap hack —
`.cm-editor:has(.cm-inplace-menu:not([hidden])) .cm-inplace-selbar { display:
none !important }` — duplicated a fix stylo shipped natively in 0.5.0 ("the
bar now yields while the menu is open and returns when it closes"). Rather
than assume the changelog entry made sympose's rule redundant, disabled the
rule locally and re-ran the same Playwright check: with `selectionUI: "bar"`,
selecting text, then right-clicking it, the bar (`.cm-inplace-selbar`) still
correctly dropped to `display: none` the instant the context menu
(`.cm-inplace-menu`) opened — stylo's own fix, unassisted. Removed the rule.

### `[[wikilink]]` autocomplete (`wikiLinkSource`, stylo 0.7.0)

The first of ADR-080's two explicitly-deferred gaps, now buildable:

- `ui/src/lib/vault-wikilink-completions.ts` (new) — `matchWikilinkTargets(tree,
  query)` flattens the vault tree to a deduped set of note filename stems (the
  same "bare stem, no folder path" convention `findNoteByWikilink` already
  resolves a *click* against), ranks prefix-match before substring-match, both
  case-insensitive, caps at 20 candidates (stylo does no re-ranking or
  filtering of its own).
- `app-shell.tsx` — `wikiLinkSource` is `read once, at mount` per stylo's own
  contract, so the function identity handed to `<Stylo>` has to survive a
  vault-tree refetch (persona switch, a new note, ADR-083 create) without a
  remount. Built off a ref (`vaultTreeRef`, kept current every render) wrapped
  in a `React.useCallback(() => …, [])` with an empty dependency array — the
  callback's identity never changes, but it always reads the live tree.
- `markdown-panel.tsx` — new optional `wikiLinkSource` prop, forwarded
  straight to `<Stylo>`.

Verified against a mocked vault tree via Playwright: typing `[[Grea` inside
plain prose surfaced `Great Ideas` (a mocked note two folders deep) in the
`@codemirror/autocomplete` dropdown. Also confirmed the trigger is correctly
inert *inside* a fenced code block, matching stylo's own documented scope —
first attempt at the check placed the caret there by accident (`Ctrl+End`
landed inside the fence in the test fixture) and got a `null` result, which
turned out to be the feature working as specified, not a wiring bug.

`![[embed]]` transclusion (`embedSource`, stylo 0.8.0/0.9.0 — the other
ADR-080 gap) stays deferred; it needs real resolution logic (fetch the target
note, parse `#heading`/`#^blockid`/`|size` suffixes, guard against embed
cycles), not a token or prop flip. Scoped as a separate follow-up.

## 2. Audit notes — helpful, unusual, not helpful

Helpful:

- The CHANGELOG discipline (Keep a Changelog format, a `BREAKING` marker used
  exactly once across nine releases) made the 0.4→0.9 jump a five-minute read
  to clear as safe, rather than a diff-and-pray.
- Every new capability in this window (`--stylo-font-size`,
  `--stylo-font-family`/`-mono`, `wikiLinkSource`, `embedSource`) maps
  directly onto something sympose's own integration journal had already
  flagged as a workaround or a deferred gap — stylo's roadmap and sympose's
  "Deficiencies found… tracked upstream" list were tracking the same problems
  from both sides independently.

Unusual, worth a second look but not urgent:

- **`--stylo-surface-floating` predates sympose's own adoption.** It shipped
  in stylo 0.2.0 — before ADR-080 was ever written — specifically so a host
  setting `--stylo-bg: transparent` (sympose's exact situation) keeps floating
  chrome opaque. Sympose's integration reached for a hand-rolled `!important`
  block over four internal class names instead
  ([index.css:298-317](../../../ui/src/index.css)). Not swapped in this pass:
  that block also carries blur/radius/shadow/row-padding sympose wants that
  the token alone doesn't give, so it's a partial tidy at best, not a bug.
  Flagging for whoever next touches that block.
- **ADR-080 and reality have drifted on the install method.** The ADR's
  Decision section states stylo is "install[ed] as a git dependency… pin a
  commit or tag rather than tracking `main`." `ui/package.json` has actually
  had a plain npm-registry range (`^0.4.0`, now `^0.9.0`) the whole time —
  `@damiro/stylo` was published to the registry shortly after ADR-080 was
  written and the install method changed without the ADR text catching up.
  Not touched here (historical ADRs are a record, not live docs) — flagging so
  someone adds an addendum note.

Not helpful / real friction, though none of it blocked this upgrade:

- No GitHub issues exist on `studiodamiro/stylo` — the prior "flagged
  upstream" deficiencies (floating-chrome background, `.cm-editor` font-size,
  the selection-bar/menu race) were tracked only in sympose's own journal and
  fixed directly in stylo's source, both repos being the same author. Works
  fine at this scale; would not scale to a stylo with outside contributors or
  users who can't just go fix it themselves.
- `wikiLinkSource` and `embedSource` share the same "read once, at mount"
  contract as `inPlace`/`mode` — reasonable given stylo's documented
  config-lifecycle stance, but it means every host wiring live data through
  either prop has to independently discover and apply the same ref-plus-stable-
  callback pattern this entry used. A wiki guide callout (stylo already has an
  "Integrating Stylo" guide) would save the next host from re-deriving it.

## 3. Is stylo worth it? — compared against known alternatives

Asked directly, after living in the upgrade: yes, and not as a close call —
the deciding constraint (Sympose's "the file on disk is the only truth, no
shadow model" vault philosophy) structurally disqualifies most of the
well-known competition rather than just ranking below stylo.

**Round-trip fidelity is the filter.** `vault_write` and every other part of
the system treat a note as a plain Markdown string. That rules out the entire
category of editors built on a rich-document-tree model:

- **TipTap / Milkdown / BlockNote** — all ProseMirror underneath. They keep
  their own AST as the source of truth and *serialize* to Markdown on save —
  exactly where frontmatter, `[[wikilinks]]` (not standard Markdown, needs a
  custom node type), and embedded math risk silently mangling on a
  round-trip. Evaluated and rejected explicitly in ADR-080's "Alternatives
  rejected."
- **Lexical** (Meta) — same category, same risk, via its own node tree.
- **Toast UI Editor** — mature and popular, but the same
  WYSIWYG-over-an-internal-model shape, and considerably less themeable to
  Sympose's degree (no equivalent of the `--stylo-*` token contract).
- **EasyMDE / SimpleMDE** — genuinely canonical-Markdown-in/out (correct on
  the one axis that matters most), but CodeMirror 5, no in-place live
  rendering (raw source or a separate preview pane, not Obsidian's live-
  preview feel), no wikilinks, no embeds, no frontmatter handling. Adopting
  it would mean rebuilding most of what stylo already has.
- **Raw CodeMirror 6, no wrapper** — this is what stylo *is*, minus the
  decoration canvas, wikilink/embed/frontmatter layer, and theming contract.
  Building that in-house is the "keep the mock, build a custom editor" option
  ADR-080 rejected as pure reinvention of a solved problem.

The pool of tools satisfying "plain Markdown string in, plain Markdown string
out, with a live in-place canvas" is close to empty besides stylo — it wasn't
picked over equals, it's nearly the only thing in its category.

**Real costs, from actually running it:**

- Pre-1.0, single maintainer, zero outside community — no GitHub issues on
  `studiodamiro/stylo`, no outside contributors, no battle-testing beyond this
  one consumer (see §2's "Not helpful" notes above).
- API surface still has gaps — sympose still reaches into undocumented
  `.cm-inplace-menu-*` internals for menu geometry (§2's `--stylo-surface-
  floating` note).
- A documented, unfixable platform limitation: `toolbar.sticky` can vanish
  mid-scroll on iOS Safari, a Chromium/WebKit compositing quirk with no
  available fix from web content.
- No ecosystem — no plugin marketplace, no collaborative-editing story
  (Yjs et al.), no third-party themes. Whatever Sympose needs beyond what
  exists, Sympose builds or requests upstream.

**What offsets it:** the maintenance-risk profile is unusual here because the
maintainer is a session away, not a stranger on GitHub. Every gap the
original integration flagged — font tokens, the selection-bar race, wikilink
autocomplete, embeds — landed within about a day of being written down,
because it's the same author building both repos. That feedback loop isn't
available from a dependency on TipTap or Toast UI Editor; the honest tradeoff
is pre-1.0 churn and being the only real-world user, in exchange for landing
fixes faster than a mainstream dependency's own release cadence would.

## 5. Features & configuration surface — what's shipped upstream but not wired

A pass over stylo's actual prop/config surface against what `markdown-panel.tsx`
and `use-editor-preferences.ts` connect, verified by grep against both repos
rather than inferred from the docs:

- **`<StyloToolbarSettings />` (stylo 0.4.0) is a complete, ready feature,
  entirely unused.** An opt-in component, exported from
  `@damiro/stylo/toolbar-settings`, that lets the *end user* drag-and-drop
  reorder / add / remove toolbar buttons — controlled (`value`/`onChange`,
  host owns persistence), with `@dnd-kit/core`/`sortable`/`utilities` as
  peer dependencies externalised from the bundle until actually imported, so
  it costs nothing sitting unused. Sympose hard-codes a fixed `TOOLBAR_ITEMS`
  array in `markdown-panel.tsx` instead. Settings › Markdown editor already
  exists as the natural home for it.
- **`onLinkClick` (plain `[text](url)` links) isn't wired to `<Stylo>` at
  all.** Grepped both files: `onWikiLinkClick` is connected, `onLinkClick`'s
  only match in `ui/src` is inside `<FrontmatterCard>`, unrelated to the note
  body. A plain Markdown hyperlink in the in-place canvas is very likely
  inert on click today — nothing opens it.
- **Callout colors never got the same treatment the fenced-code syntax
  palette got.** Stylo ships per-type callout accent tokens —
  `--stylo-callout-note` / `-tip` / `-warn` / `-danger` / `-example`
  (`src/inplace/theme-callout.ts`) — defaulting to stock saturated hex
  (`#3b82f6` blue, `#22c55e` green, `#f59e0b` amber, `#ef4444` red, `#a855f7`
  purple). This is the identical "stock hex with no relation to Sympose's
  OKLCH accents" problem the fenced-code syntax colors were deliberately
  rebuilt to fix during the original integration — callouts were simply never
  reached. An Obsidian-style `> [!warning]` block in a real vault note renders
  clashing colors today; nothing surfaced this because no test note has used
  one yet.
- **Two of stylo's four modes are unreachable from Settings.**
  `EditorSurface` (`use-editor-preferences.ts`) only offers `"in-place" |
  "source"`, though stylo also has `"preview"` (rendered, read-only) and
  `"split"` (source + rendered side-by-side). ADR-080 reasoned about which
  mode should be the *default* (in-place, correctly), not about permanently
  excluding the other two from ever being user-selectable — a legitimate gap
  for anyone who'd want a read-only review pane or a side-by-side view.
- **`inPlace.decorations` (per-construct toggles) isn't exposed.** Stylo lets
  a host turn off individual decorations — tables, embeds, math, callouts,
  etc. — via `InPlaceDecorationToggles`; no sympose preference reaches it.
  Minor: a power-user knob, not a gap anyone has asked for yet.
- **No toolbar affordance inserts a new table.** `"table"` is explicitly
  excluded from `TOOLBAR_ITEMS` (same as `link`/`wikilink`/`hr`/`frontmatter`/
  `math`, per the file's own doc comment). Editing an *existing* table still
  works via the in-place canvas's interactive table editing regardless — this
  is a discoverability gap for starting one from scratch, not a missing
  capability.

## 6. Follow-ups (not done here)

From this session:

1. `embedSource` (`![[ref]]` transclusion) — scope and build once real vault
   content shows it's load-bearing, per the original ADR-080 call.
2. `--stylo-surface-floating` vs. the hand-rolled floating-chrome background
   override — low-priority tidy, not a bug.
3. ADR-080's "git dependency" text vs. the actual npm-registry install —
   needs an addendum note, not a rewrite of the historical record.

Re-audited against the *2026-09-10 integration entry's* own follow-up list
while writing this one — one is resolved, two are still genuinely open, both
higher-priority than anything above:

4. **Conflict detection on save — still the one gap with real data-loss
   risk, still unbuilt.** ADR-081 states it outright: "Autosave writes on a
   debounce with no conflict detection — last write wins." Sympose is a
   multi-agent hub; a persona's own tool-calling backend can write the same
   note a human has open in stylo, and the human's next autosave (or explicit
   save) silently overwrites whatever the agent just wrote, with no warning
   either direction. This was the original integration's #1 flagged follow-up
   and remains the most consequential item in this whole audit — worth
   scoping before autosave sees any wider default-on push.
5. **No unsaved-changes indicator.** `markdown-panel.tsx` already tracks a
   dirty state internally (`savedTextRef` vs. the live `joinNote(...)`
   comparison, driving the autosave debounce and the no-op guard on save) —
   the data exists, there's just no UI surfacing it. Minor next to #4, but
   still genuinely missing.
6. **Find/replace needed no wiring — already fully functional, confirmed
   today.** The 2026-09-10 entry listed `@codemirror/search` as a pending
   "wire it in" follow-up. It didn't need one: stylo bundled `search` +
   `searchKeymap` unconditionally into every editing surface back in its own
   0.3.0 (`src/editor/extensions.ts`), before sympose's dependency floor even
   started at 0.4.0. Verified today with a scratch Playwright check —
   `Cmd-f` (the actual `Mod-f` on this platform; a first pass with `Ctrl-f`
   gave a false negative, since CodeMirror's `Mod` resolves to `Cmd` on
   macOS) opens stylo's own restyled search panel with zero sympose code.
   Correcting the record rather than re-opening it as a task.

New from this session, not on either prior list:

7. **No permanent regression coverage for round-trip fidelity — the one
   guarantee §3 above rests the entire "why stylo" argument on.** Every check
   in this entry (font tokens, the menu/bar fix, wikilink autocomplete, the
   find-panel correction) was verified with a scratch Playwright script,
   screenshotted, then deleted — same pattern the original integration used.
   That's fine for a one-off upgrade audit, but the actual load-bearing
   property — a note round-trips through stylo (frontmatter, wikilinks,
   embeds, math, tables) without loss — currently has zero coverage in
   `.venv/bin/pytest` or anywhere else that runs unattended. If a future
   stylo bump ever regresses that guarantee, nothing catches it before a real
   note does. Worth a small permanent Playwright (or component-level) fixture
   — load known-tricky content, round-trip it, assert byte-for-byte (or
   intentionally-normalized-only) equality — checked into `ui/`, not
   scratch-and-delete.

From §5's features/configuration audit — roughly in priority order:

8. **Rebuild `--stylo-callout-*` from Sympose's own palette**, the same move
   already made for fenced-code syntax colors. Highest priority of this
   batch: the only one that's a visible, user-facing rendering bug the moment
   a real vault note uses a callout, not a missing nicety.
9. **Wire `onLinkClick`** on the main `<Stylo>` instance so plain Markdown
   links do something (open in a new tab, at minimum) — currently likely
   dead on click.
10. **Surface `<StyloToolbarSettings />`** under Settings › Markdown editor —
    a complete upstream feature, no new sympose-side mechanism needed beyond
    a persistence cookie matching the existing preferences pattern.
11. `"preview"` / `"split"` as selectable `surface` values, `inPlace.decorations`
    toggles, and a toolbar "insert table" affordance — lower priority, no one
    has asked for any of the three yet.
