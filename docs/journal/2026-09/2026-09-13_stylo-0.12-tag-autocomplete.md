### Version bump

### Candidate source: the nebula's graph, not a new client-side scan

The blocked entry flagged this as worth checking before building anything:
does a tag index already exist server-side? It does — `GET /api/vault/graph`
(ADR-078) already returns each note's frontmatter `tags: string[]`, and
[nebula-graph.ts](../../../ui/src/lib/nebula-graph.ts)'s `buildMasterGraph`
already folds that into one `tag:<name>` hub node per distinct tag (used
today to render the Knowledge Nebula's tag hubs). Wrote
[vault-tag-completions.ts](../../../ui/src/lib/vault-tag-completions.ts)'s
`matchTagTargets(graph, query)` to just read that pre-built index back out —
filter `graph.nodes` for `isTag`, rank prefix-match first then
substring-match (both case-insensitive), cap at 20 — the same ranking
`matchWikilinkTargets` already uses for `[[wikilink]]`. No new backend
endpoint, no separate frontmatter walk.

### Sharing one fetch instead of two

Reusing the nebula's graph meant reusing its fetch too. `useNebulaGraph()`
was previously called only inside `<AmbientNebula>`, lazy-mounted after
first paint so its fetch stays off the shell's TTFT path alongside the
`react-force-graph` chunk. Calling it a second time from
[app-shell.tsx](../../../ui/src/routes/app-shell.tsx) for `tagSource` would
have raced two independent `GET /api/vault/graph` requests against each
other the moment both were live at once. Lifted the one `useNebulaGraph()`
call up to `app-shell.tsx` instead — `<AmbientNebula>` now takes `graph`/
`source` as props rather than fetching its own — so the ambient layer and
the editor's tag completion read the same in-memory graph. The fetch itself
is a small `fetch()` call, not CPU work, so moving it earlier (it now starts
at shell mount instead of waiting for the idle-deferred nebula chunk) was
judged not to compete with TTFT the way the `react-force-graph` bundle load
does.

### Wiring, mirroring `wikiLinkSource` exactly

- `tagSource` threaded `app-shell.tsx` → `markdown-panel.tsx` → `<Stylo>`,
  same ref-plus-stable-callback pattern (`nebulaGraphRef`, mirroring
  `vaultTreeRef`) so the function identity handed to stylo stays stable
  across a graph refetch, per stylo's "read once, at mount" contract.
- No new CSS — the `[data-slot="markdown-panel"] .cm-tooltip.cm-tooltip-autocomplete`
  rule already themes any `@codemirror/autocomplete` popup generically, not
  scoped to wikilinks, confirmed unchanged in `index.css`.

## Follow-up, same day: inline body `#tag` → frontmatter sync

Surfaced immediately after confirming the above: a `#tag` typed and saved in
the body never showed up in `<FrontmatterCard>`'s `tags:` pills. Traced —
[frontmatter-card.tsx](../../../ui/src/components/sympose/frontmatter-card.tsx)
only ever renders the note's parsed YAML `tags:` list; nothing reads the body
for inline hashtags. Not a deliberate Obsidian-style "two separate tag
namespaces" design — just incidental, confirmed by the fact that
[vault.py:1452](../../../sympose/vault.py#L1452)'s `_sync_frontmatter_tags`
already does exactly this kind of body-to-frontmatter merge, just scoped
today to the agent's own `write_daily_note` path, never the human editor's
`PUT /api/vault/note` save.

Decided, after discussion, to sync one-directionally (body → frontmatter
only; deleting a body `#tag` never deletes it from frontmatter) and to feed
the merge on save rather than live per-keystroke.

**Extraction rules** — landed in
[extract-inline-tags.ts](../../../ui/src/lib/extract-inline-tags.ts), unit-
verified against 11 cases (start-of-line, mid-sentence, mid-word rejection,
`# Heading` rejection, `#1234` rejection, a bare URL fragment, inline code,
a fenced code block with a shebang and a `#` comment inside it, and
case-insensitive dedup) before wiring it in:

- `#` must sit at start-of-line or after whitespace — mirrors stylo's own
  live trigger (`tag-complete.ts`'s `(?<=^|\s)#[^\s#]*$`) exactly, so a
  mid-word `#` or a URL fragment (`page#section`) never counts.
- A digit immediately after `#` is excluded (`#1234` reads as an
  issue/anchor reference, not a tag) — same as stylo's live rule.
- Fenced (```` ``` ````) and inline (`` ` ``) code stripped before scanning —
  stylo gets this for free from CodeMirror's parser; a plain-text
  post-hoc scan doesn't have one, so `#include`, `#define`, a shebang, and a
  CSS `#fff` needed an explicit strip.
- Character set capped to `[a-zA-Z0-9_/-]` — narrower than stylo's own
  "anything but whitespace/#" query (which is bounded by the live caret, not
  a real word boundary), so `#project.` at a sentence's end extracts
  `project`, not `project.`. Matches the one prior precedent in the codebase,
  `_sync_frontmatter_tags`'s `[a-zA-Z0-9_\-]+`, plus `/` for Obsidian-style
  nested tags — `#journal/engineering` is **one** tag named
  `"journal/engineering"`, not two, matching how this project's own docs
  frontmatter already uses that exact tag.
- New tags are lowercased before merging (dedup against existing tags is
  also case-insensitive) — settled after a detour into tag-casing
  conventions generally: kebab-case/lowercase is the de facto standard
  across tagging systems (GitHub labels, npm `keywords`, Obsidian community
  practice) for a concrete reason, not just style — camelCase and
  case-insensitive dedup are fundamentally at odds, since folding
  `workInProgress` for dedup collapses it to `workinprogress`, destroying
  the readability camelCase was chosen for. This project's own docs were
  already kebab-case (`upstream-request`) without anyone deciding it as a
  rule.

**Wiring** — [markdown-panel.tsx](../../../ui/src/components/sympose/markdown-panel.tsx):
a new `syncInlineTags(frontmatter, body)` sits next to `joinNote` (both are
note-assembly concerns). Runs inside `saveNote()` before `joinNote` — parses
the current frontmatter, extracts inline body tags, appends whatever isn't
already present (case-insensitively), then both re-serializes the frontmatter
for the save payload *and* calls `setFrontmatter(...)` so `<FrontmatterCard>`
updates in the same tick, no server round-trip needed for the UI to reflect
it. Also flips `frontmatterEditedRef.current = true` when a merge actually
adds something — without that, `joinNote` would keep splicing the *original*
byte-for-byte `---` prefix onto the body (its normal behavior when the card
was never touched) and silently drop the merge. `null`/unparseable
frontmatter (no `---` block, or something `parseFrontmatter` can't
round-trip) is left alone, same fallback `<FrontmatterCard>` itself already
uses — no note gains a frontmatter block it didn't already have.

Feeding the vault-wide tag index (so a tag introduced only in one note's body
becomes an autocomplete suggestion in every other note) needed **zero** new
backend work: `overwrite_note` ([vault.py:1046](../../../sympose/vault.py#L1046))
already calls `_update_manifest_if_enabled` after every save, which re-reads
the file's frontmatter and does a single-node patch into the ADR-078
manifest — the same manifest `GET /api/vault/graph` serves, which is what
`matchTagTargets` reads. Once the merged tag lands in the file's frontmatter
block on disk, the existing pipeline picks it up for free.

`npm run typecheck` and `npm run build` clean, rebuilt `sympose/webui/`. No
interactive browser check yet on this specific follow-up.

## Follow-up, same day: autosave was baking in half-typed tags

Caught live, immediately: autosave's 1.5s debounce fires on any typing pause,
including mid-word inside a tag the user hasn't finished typing yet. Typing
`#css` slowly enough produced `mountain`, `tag`, `tag-`, `cs`, and `css` all
landing as separate permanent frontmatter pills — every intermediate
fragment autosave happened to catch got merged in, and because the sync is
additive-only by design (deleting a body `#tag` never removes it from
frontmatter, per the earlier decision), none of the stale fragments ever got
cleaned back out on their own.

Fix: `syncInlineTags` now only runs on an explicit save (toolbar button,
⌘/Ctrl-S) — `saveNote`'s existing `silent` flag already distinguishes that
from autosave, so the gate was a one-line change in
[markdown-panel.tsx](../../../ui/src/components/sympose/markdown-panel.tsx).
Autosave still persists the body itself as before (data-loss protection is
unaffected); it just no longer touches frontmatter tags. An explicit save is
a deliberate "I'm done" moment, so whatever's in a `#tag` at that instant is
the tag the user meant — the earlier design didn't distinguish the two save
paths and should have from the start.

The already-polluted pills on damiro's own test note (`tag-`, `cs`) are real
vault content now — not cleaned up here, since editing a user's note content
without being asked is out of scope for this session; each pill already has
its own `×` to remove by hand.

`npm run typecheck` and `npm run build` clean, rebuilt `sympose/webui/`.

## Follow-up, same day: flush a save when leaving a note

Requested as a safety net for "forgetful" users who rely on autosave being
on (it isn't, by default) or just don't hit save before switching notes.
Added a flush that fires on note switch or the panel unmounting entirely —
not on hiding the panel while staying on the same note, since nothing is
discarded there (`body`/`frontmatter` stay in React state either way, so
there's no actual loss to guard against).

The straightforward version of this — an effect keyed on `path` whose
cleanup calls `saveNote()` — turned out to have two real races, both caught
before shipping rather than after:

1. **A ref updated every render, read from the cleanup, is the standard
   pattern for "always call the latest version" — but `saveNote` used
   `path` (the prop) as both its dirty-check target and its `PUT` target.**
   On a note switch, `path` moves to the next note a full render before that
   note's fetch resolves; a ref updated during that same render would
   already point to a `saveNote` closure carrying the *new* path, while
   `body`/`frontmatter` state still held the *old* note's content —
   `saveVaultNote(path, ...)` would silently write the leaving note's text
   onto the arriving note's file.
2. **Putting `saveNote` directly in the flush effect's own dependency
   array** (so its closure would stay fresh) re-runs that effect — cleanup
   included — on every keystroke, since `saveNote` gets a new identity
   whenever `frontmatter`/`body` change. That would have fired the flush
   (and the tag sync, since it's meant to run here) on every single
   keystroke, reintroducing the mid-word-tag bug from two entries up in a
   worse form.

Fixed by re-pointing `saveNote` itself at `loadedPathRef.current` — the note
`body`/`frontmatter` state actually holds — instead of the `path` prop, for
both its guard and its `saveVaultNote` target. `loadedPathRef` only updates
once a fetch actually lands (existing behavior, see its own comment above
`savedTextRef`), so during the gap after `path` has moved on but before the
new note has loaded, it still correctly names the *leaving* note. That
removed `path` from `saveNote`'s own dependency list entirely, which in turn
made the plain "ref updated every render" pattern safe for the flush effect
— `saveNoteRef.current` at cleanup time is guaranteed to still be scoped to
the leaving note, and the flush effect's own dependency array can stay just
`[path]`, so its cleanup only ever fires on an actual switch or unmount.
Sanity-checked the ordering with a small throwaway Node script simulating
the render sequence (not committed) before trusting it.

Silent (no toast — a background safety net, not a user-initiated save) but
still syncs tags, unlike autosave: leaving a note is a deliberate-enough
signal that whatever's in a `#tag` at that moment is what was meant, not a
timer coincidentally landing mid-word.
