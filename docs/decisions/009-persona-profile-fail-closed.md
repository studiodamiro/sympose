# 009 — `profile.py`'s final shape: fail-closed resolution, settings-backed default

## Context

`profile.py`'s `get_profile` caught `except (OSError, yaml.YAMLError): pass` and fell back to a whole-vault profile (`vault_folders: ["*"]`) whenever anything went wrong loading `<profiles_dir>/<handle>.yaml`. `FileNotFoundError` is an `OSError` subclass, so "no file matches this handle" — the ordinary state of a typo'd or not-yet-configured persona — hit the exact same fallback as "no `profiles/` directory configured at all." ADR 006 named this gap and deferred it, at first under-describing it as "a corrupted file," then correcting itself once a full-backend review live-verified it also fires for a handle with no file whatsoever, bypassing read/write/delete and chat-grounding sandboxing. ADR 006 tracked the real fix as "the seed of a future 'build the full agent profile' milestone," reasoning that a narrow patch (tightening the `except`) wouldn't also close the same fallback firing on an unsafe/traversal path, and that every persona-scoped route shared the identical gap.

Rather than patch narrowly and reshape this module again for the next milestone, this record gives `profile.py` its final shape now. Two things made that tractable without guessing at undesigned future features (soul/memory/expertise, still separate, later-named `VISION.md` milestones): the dashboard frontend (`ui/src/lib/personas.ts`) already defines and calls a `GET /api/personas` contract the backend never implemented — `{default, personas: [{handle, name, title, model, skills, is_default}]}` — falling back to a static Samantha-only list when unreachable, so shipping it was additive, not invented; and legacy already solved "what does the default persona mean, and can a user change it" via `sympose/config_settings_runtime.py`'s `runtime.default_persona` config key, `"samantha"` as its factory-default value, read live everywhere legacy needed it rather than hardcoded per call site. This repo already has the matching mechanism, `settings_store.get(key, default)`/`set(key, value)`, already used identically for `active_vault` and (read-only so far) `chat_model`.

## Decision

**Fail-closed contract.** `get_profile(handle) -> dict | None` now splits its fallback on **directory existence**, not on which exception fired: no `profiles/` directory at all returns the whole-vault fallback, unchanged — the intended day-one default for a fresh checkout — but once a `profiles/` directory exists, an unknown handle, an unsafe/traversal path, or a file that fails to parse all return `None`, failing closed rather than silently widening.

`resolve_profile(persona: str | None) -> dict | None` resolves a falsy `persona` through `resolve_default_persona()` (below), then applies the same rule — with one safety net: if the *resolved* handle is the hardcoded `FACTORY_DEFAULT_PERSONA` ("samantha", the one handle guaranteed to ship committed) and its file has gone missing too, it still falls back to whole-vault access under that handle. A *configured* custom default whose file has gone missing does **not** get that safety net — it fails closed instead, because extending the net to any configured handle would silently reopen the exact bug this record fixes, just reached through the new settings key instead of a typo. Recoverable by fixing the file or the setting; consistent with the "self-inflicted, single-user, local-first, no other threat actor" reasoning this project already applies elsewhere (ADR 006).

An explicitly-passed unknown handle (the `persona` query param/body field itself, not the default) always propagates `None`, never the fallback — exactly the gap being closed. Every persona-scoped route (`server_handlers.py`, `server_trash_handlers.py`, `server_search_handlers.py`) now calls a new shared `require_profile(persona)`, raising 404 instead of proceeding on `None`. This closes the bug on read-only routes too (`list_trash`, `search_vault`), not just the write routes ADR 006's original framing focused on — a `GET /api/vault/trash?persona=typo` today silently listed the *entire vault's* trash. `engine/turn.py`'s `run_turn` gets the same treatment via a new `PersonaNotFoundError`, defensive-only today (the CLI's picker only ever offers real roster handles) but no longer able to crash with a bare `AttributeError` on a `None` profile.

**Settings-backed default persona.** `resolve_default_persona()` reads `settings_store`'s `default_persona` key, falling back to `FACTORY_DEFAULT_PERSONA = "samantha"` when unset — mirroring `engine/model.py`'s `resolve_model()` exactly, and legacy's `runtime.default_persona` before it. Every site that used to hardcode the literal `"samantha"` (`server_models.py`'s 6 Pydantic field defaults, `server.py`'s 7 `Query` defaults, `cli/app.py`'s startup persona pick) now either defaults to `None` and lets `resolve_profile` do the actual resolution, or calls `resolve_default_persona()` directly. No route or command to *change* the setting exists yet — same posture `chat_model`'s own settings-store read path already has, no writer yet either. `settings_store.set("default_persona", ...)` already works the moment something needs to call it; building that UI is separate, smaller scope, not gated on this record.

**Roster + additive schema.** `list_profiles()` is the one canonical roster function this module owns now (`get_profile`, normalized, over every `profiles/*.yaml` handle) — shared by the CLI's `list_personas()` (which stops hand-rolling its own glob walk) and the new `GET /api/personas` route (`server_persona_handlers.py`). Every profile dict now also carries `model` and `skills` keys — `model` left as whatever the YAML says or `None`, `skills` defaulting to `[]` — satisfying the frontend's existing contract shape without inventing behavior: neither field is wired into `run_turn`'s actual model selection or any skill-filtering logic yet, both purely additive/display-only until a later milestone decides personas should override those. Deliberately, `get_profile`/`_normalize` never import `sympose.engine.model` (which `import litellm`s at module scope) — that module runs on *every* dashboard route via `get_profile`/`resolve_profile`, so filling a model default there would make litellm a transitive import of all of them, not just chat. The one caller that needs a real display fallback (`server_persona_handlers.get_personas`) resolves it there instead, scoped to a route called once per roster load.

## Consequences

An empty-but-existing `profiles/` directory now yields an empty roster (`[]`), not a synthetic Samantha entry — intentional, consistent with the fail-closed posture once a profiles directory is actually configured, not a bug to "fix" back into a silent default later. `list_trash`/`search_vault`/every CRUD route now 404 for an unknown persona instead of silently defaulting; any client relying on the old fail-open behavior (none exist today — no auth, local dev only, per `server.py`'s own docstring) would need updating. `vault_graph.py`'s persona-scoping, `vault_manifest_build.py`'s unused `folders`/`meta` fields, and `engine/turn.py`'s unused `TurnResult.grounding` field remain parked, unrelated to this record — none of them block or are blocked by it. Soul/memory/expertise content stays exactly as deferred (`PLACEHOLDER_SOUL` in `engine/prompt.py`).

## Alternatives rejected

- **Narrowing the `except` clause alone** (`except OSError` → a narrower catch on just `yaml.YAMLError`, or explicitly re-raising `FileNotFoundError`). Rejected: it wouldn't also close the identical fallback firing on the unsafe-path branch, and it leaves every downstream caller still assuming `get_profile` never returns anything but a usable dict.
- **A hardcoded `DEFAULT_PERSONA` constant** replacing the scattered `"samantha"` literals. Rejected in favor of a live settings-store value — a same-shaped constant is still not user-changeable, and legacy already proved the settings-store shape is the right one for exactly this key.
- **Leaving `list_trash` silently-empty for an unknown handle** instead of 404ing (matching its existing "no vault configured" graceful-degradation path). Rejected: that's the same fail-open shape being fixed everywhere else, just reached through a GET route instead of a write route.
