# 015 — Context budget: an overflowing prompt is cut silently, so the engine must size it

> **Scope of the measurements: Ollama and `gemma2:9b` only.** Every number below was measured on one runtime (Ollama 0.33.3) with one model (`gemma2:9b`, the default local model), at temperature 0, with synthetic chat turns. Other Ollama models, other Ollama versions (its default window and its truncation rule are Ollama's to change), and cloud models (which have their own, usually much larger, windows and their own overflow behavior, typically an error instead of a silent cut) were not measured. Treat the figures as the local default's behavior, not as a property of Sympose or of models in general, and re-measure before generalizing.

## Context

Nothing in the engine sets the model's window or checks that a prompt fits it. The prompt is the system prompt (soul, engine rules, the grounding block) followed by up to 20 turns of history (`session.history_as_messages`, a count and not a size) and the new message, and the reply must fit in the same window. Grounding passages (ADR 014) made the system prompt larger than the earlier one-line snippets, so this was measured before anything was built on top.

## Measured (Ollama 0.33.3, `gemma2:9b`)

**The window is 4096 tokens by default.** Ollama reports it in `ollama ps`; the model itself supports 8192, and Sympose never asks for more (no `num_ctx` is set anywhere). One token is roughly three quarters of an English word, so 4096 tokens is roughly 3,000 words.

**What the prompt costs.** The shipped soul plus the engine rules is about 450 tokens. Retrieved notes are part of that same system prompt and count toward the window: only passages are sent, never whole notes, each capped at 400 characters and carrying its title, path, and heading. Five passages of about 200 characters (what was measured) add about 280 tokens, roughly 55 each; at the 400-character maximum they add an estimated 450 to 550 (not measured), so the system prompt is about 730 tokens typically and up to roughly 1,000 in the worst case. The passages are not stored in the session history and are retrieved fresh each turn, so they do not accumulate across turns. That leaves about 2,700 to 3,000 tokens for history once room for the new message and the reply is set aside.

**How many turns fit** (with the typical 730-token system prompt; the worst case fits about 10 percent fewer; one turn is a user message plus a reply; the 20-turn history cap applies first for short chats):

| Reply length | Tokens per turn | Turns that fit |
|---|---|---|
| about 60 words | about 95 | 30 or more, so the cap of 20 applies and nothing overflows |
| about 120 words | about 160 | about 19 |
| about 200 words | about 240 | about 12 |

Measured directly with the real prompt builder and 20 turns: about 2,600 tokens at 60-word replies, 3,900 at 120 words (at the limit), 5,600 at 200 words (over it). Only three real replies existed to sample (average 15 words), too few to say what typical use looks like.

**An overflow is silent and not safe.** Beyond the window Ollama cuts the prompt without an error. A fact stated in the oldest turn was lost, and returned when the window was raised to 8192. The system prompt was not protected: at 56 turns it was partly gone (a "end every reply with a given word" rule stopped being followed and the model invented a detail), and at 70 turns it was entirely gone (asked to quote its instructions, the model quoted the chat). The soul and the engine's grounding rules live in the system prompt, so an overflow can silently remove the honesty rules.

**The reported token count cannot show an overflow.** Ollama's `prompt_eval_count`, which litellm returns as `prompt_tokens` on a streamed call when usage is requested, is the size after the cut: it stayed at about 4,070 to 4,090 or fell to about 2,050, never above the window. A meter fed only this number reads full or fine exactly when the prompt is being cut.

**What a bigger window costs, and what changing it costs** (same Ollama and model): the loaded `gemma2:9b` takes 6.3 GB at a 4096 window and 6.6 GB at 8192, so doubling the window costs about 0.3 GB on this model (a much smaller step than a full-attention model would need). The cost grows with the window and differs a lot by model: `qwen3:8b` takes 5.9 GB at 4096, 9.9 GB at 32768 and 11 GB at its own maximum of 40960 (all on the GPU on this 24 GB machine). `gemma4:e4b` (maximum 131072) reported 9.6 GB at 8192 and 3.9 GB at 131072, which does not make sense and is not trusted. A full-attention model with a 131072 maximum is estimated, from its architecture and not measured (none installed), to need roughly 15 GB more for the window than at 4096, which is why the automatic default is capped below. Asking Ollama for a different window than the one the model is loaded with forces a reload: the first turn after the change took 3 to 4 seconds longer, later turns were normal.

**How accurate a token count the engine can make itself.** `litellm.token_counter` against Ollama's real `prompt_eval_count` on real prompts (the soul and rules, five passages, ten turns of chat): prose 2 to 4 percent low, code-like text 12 percent low, Japanese text 64 percent high (an over-count, the safe direction, but it makes the trimming aggressive for such chats). Five prompt shapes were measured, so the margin below is a measured floor, not a guarantee. `num_ctx` and `max_tokens` passed to `litellm.completion` do reach Ollama (the loaded window read back as 8192; a reply limited to 6 tokens stopped after 6 with a `length` finish).

## Decision

The engine sizes the prompt itself and never relies on the runtime's cut.

**Which window a turn gets** is decided per turn from the model that actually runs (the precedence in ADR 010), so switching model, or a persona with its own model, changes it. For Ollama models (`ollama/` and `ollama_chat/`) it follows the model's own maximum as the running server reports it, so it adjusts by itself when the model changes; that is the default, with no setting stored. Two limits apply to the automatic value: it is capped at 32768 tokens, because a model with a very large maximum (128k) would otherwise ask Ollama for many GB of memory by default on a machine that may not have it, and if the model's maximum cannot be read (Ollama down, a model that is not installed) it is 4096, Ollama's own default, so nothing is asked of a model that may not support more. A user who sets `context_window` has made a deliberate choice, which is kept: it applies to every model as a ceiling (a model whose own maximum is lower still gets its own, never more than it supports), it is not subject to the 32768 cap, and it persists across model changes until the user changes it. A missing, non-numeric or non-positive value means automatic; a small positive value is raised to 2048, the smallest usable window (1024 until ADR 022 grew the shipped persona's own prompt to about 940 tokens), since someone asking for a tiny window wants a small footprint and reading it as automatic would give the opposite. The result is sent to Ollama as `num_ctx`. For cloud models the window is the provider's own as litellm reports it, the setting does not apply, and `num_ctx` is not sent; if no window is known, no size trimming happens. For an installed Ollama model litellm reads the maximum from the running server (`gemma2:9b` is not in litellm's built-in table, and its 8192 came from Ollama); the lookup is cached per model in process, successes only, so a server that was down for one turn is asked again.

**The prompt is fitted to the window, in a fixed order of sacrifice.** The budget is the window minus a reply reserve (a quarter of the window up to 4096 tokens, or the user's `reply_limit` setting, never more than half the window; taken for every model, since some providers share one window between input and output) and minus a safety margin on the engine's own token count (15 percent, from the measurements above). Within it: oldest whole turns are dropped first (a user and assistant pair is never split); then, if the fixed part still does not fit, the lowest-scoring grounding passages; the soul, the engine rules and the new message are never dropped. If those three alone do not fit, the turn fails with a clear error (saying to shorten a very long message or use a model with a larger window, and to raise `context_window` if it was set) instead of letting the runtime cut the soul. **Passages left out are said to be left out**: the grounding block then reads that matching notes exist but could not be included (or that N more were left out), never "no notes matched", which would be false and would make the model tell the user the vault has nothing on the topic. Real-model check on `gemma2:9b`: with the old empty-match sentence the model said it found nothing in 3 of 3 runs; with the new wording it admitted the notes were left out in 4 of 6 runs (and in 1 of 3 in an earlier sample), so it helps but is not reliable on this model; a stronger wording did no better (2 of 6) and was not kept. Passages are only lost when the instructions, the new message and the top passage together approach the window, which takes a very long message or a very small window. The 20-turn history cap stays as a separate ceiling, a cost limit. Left-out turns remain in the session record; they are only not sent.

**The reply is capped to its reserve** for Ollama models (`max_tokens`, which litellm maps to Ollama's `num_predict`), so prompt plus reply always fit the window. The reserve scales with the window and has its own `reply_limit` setting because a fixed 1024 was shown to be too small for a reasoning model: on `qwen3:8b`, a hard question (compare two note-taking methods and propose a folder scheme) was cut off at 191 words under a 1024 limit, mid-heading, and completed as 760 words under 4096, though that took 298 seconds. Cloud replies are not capped by us. A reply that stops at the cap is marked (`ModelReply.truncated`, from the runtime's `length` finish, carried on the turn result) and the header says so; a model that spends its whole limit before writing any answer fails with a message saying so, not a bare "empty reply".

**The user is told.** A turn where turns were left out because of size (not the 20-turn cap, or the notice would fire on every turn of a long chat) carries the count, and the CLI reply header shows it (`3 older turns out of context`, and `reply cut at the length limit` for a truncated reply) behind a `show_trim_notice` setting, on by default and turned off only by an explicit `false`, the same rule as `show_grounding` (ADR 016). It is shown only on turns where something was left out.

**No history budget by default.** The default uses as much of the window as is safe: the prompt fills the window minus the reply reserve and the token margin (about 65 percent of it in real tokens at the defaults), bounded by the 20-turn history cap, and nothing else limits how much past conversation is sent. A separate, smaller limit on past conversation (a history budget, in tokens) was considered as a default and not chosen: recall did not degrade up to half the window in the measurements above, and a typical chat with short replies never reaches the slow range. What it would buy is a bounded wait on a long or resumed chat; it is recorded below as an optional knob, off by default, not built. The window itself is not shrunk for this: it costs memory, not time, and a smaller window also removes room for grounding passages and long messages.

**A context meter** (percentage, CLI first; the web UI waits for the dashboard work) is built as ADR 018, computed from the engine's own count of the full prompt, since the runtime's reported count is post-cut. Provider-reported usage is a cross-check where it is trustworthy, not the source.

Follow-up grounding (a separate slice, still to be recorded) adds a model call whose prompt also has to fit, which is why this comes first.

## Consequences

The window follows the model with no setting (`context_window` is only a user's own ceiling, `reply_limit` the reply room, `show_trim_notice` a display knob), both in the settings file for now; the CLI has no settings screen yet, and a slash command per knob is not added. The engine's token count is an estimate: the 15 percent margin costs roughly that much of the window on ordinary prose, and was measured on one model's tokenizer only, so other local models and cloud models are to be re-measured before the margin is trusted there. A chat in a language whose text the counter over-counts (the Japanese sample) loses older turns sooner than it strictly must; that is the safe error. The first turn after the window changes (a model switch that changes it, or a changed setting) is a few seconds slower because Ollama reloads the model. The reply cap means a very long answer stops at the reserve on local models (about 1,500 words at the 8192 default), and a user with a reasoning model may want `reply_limit` higher. Not yet handled: per-persona window overrides, dropping turns in larger steps so the prompt's start stays cacheable, and a truncated reply is still saved to the session as written (it is marked on screen, not in the record). The fitting loop rebuilds and recounts the prompt for each turn dropped; measured at 29 ms in the worst realistic case (20 long turns, most dropped) against a model call of seconds, so it is not optimized. If the engine's token counter itself fails, it falls back to one token per character, an upper bound that can only make trimming too eager.

**Verified live (same Ollama and model, a scratch profile, the real soul; measured with the first version's fixed 1024-token reply reserve, so the exact turn counts differ a little now).** A 22-turn chat of 460-word replies, which the 20-turn cap alone would send as about 8,000 real tokens with no room left for a reply, was fitted to 7 turns: Ollama measured 5,755 tokens actually sent against the 8,192 window, the soul and engine rules were in the prompt, the model answered from its instructions and not from the chat (the failure in the measurements above), and the session record still held every turn. In the CLI with the setting lowered to 1024, the fourth short turn showed `1 older turn out of context`. **Two costs seen there, both about latency.** A large prompt is slow to process the first time on this machine: the first turn on a resumed 22-turn chat fitted to 5,755 tokens took 45, 72 and 101 seconds to first token in three runs (it varies a lot from run to run), against about a second for the turns after it. Ollama reuses its earlier processing of a prompt's start, so the turns that follow are fast as long as the start does not change; a turn whose reply pushes older turns out changes the start, and pays again (5.3 seconds against 0.8 in the tight-window CLI run, where the prompt was small). So a wider window buys memory of the conversation at the price of a slow first turn on a long or resumed chat, visible in the recorded TTFT; The window itself costs memory, not time, when the chat is short; what costs time is a long prompt, which the 20-turn cap also bounds. The `context_window` setting is where a user makes that trade in either direction (lower to save memory or to bound the first-turn wait), and it is kept. (The live runs above used `gemma2:9b`, whose own maximum is 8192, which is also what the automatic default now gives it.) Dropping turns in larger steps, so the start stays the same for several turns, is a known refinement and not built.

**Does a fuller prompt make the model forget? Not up to half its window, on this model; what grows is the wait.** `gemma2:9b` was given two planted facts (a code and a name), early or in the middle of a chat, padded with unrelated turns to real sizes of about 0.8k, 1.7k, 2.8k and 4.1k tokens (half of its 8192 window), and asked for them back: it returned both every time (8 of 8), with temperature 0. Not tested: prompts above 4.1k, other models, facts spread over several turns. What did grow was the time to process a prompt it had not seen before (total time for a 40-token reply): about 10 to 12 seconds at 0.8k, 17 at 1.7k, 30 to 39 at 2.8k, and 81 to 100 at 4.1k, on this machine, so the wait grows faster than the prompt does. Ollama reuses its earlier work only while the start of the prompt is unchanged and the model stays loaded, so the slow case is any turn after the model was unloaded (Ollama's default keep-alive is a few minutes, so a break in the conversation, not measured here) or in a resumed session. This is the cost a smaller history would buy back, and it is why a separate limit on how much past conversation is sent (a history budget, not a smaller window) is the natural next knob; not built.

**A header caveat.** The notice takes its room before the grounded note does, so with both showing at exactly 80 columns the header runs a few cells over and wraps (ADR 016's floor keeps the filename visible over fitting).

## Not built yet (recorded so it is not lost)

Each item says what it is, why it was left out, and what would prompt building it.

- **A history budget knob.** A cap, in tokens, on how much past conversation is sent, independent of the window; a setting off by default, with a value (roughly 3,000 was floated for local models) chosen only if wanted. It bounds the cold first-turn wait (measured on one machine and model: about 10 seconds at 0.8k tokens, 30 to 39 at 2.8k, 81 to 100 at 4.1k; a resumed session or a turn after the model unloaded pays it, since Ollama reuses its earlier work only while the model stays loaded and the prompt's start is unchanged). Build it if real use shows long-reply chats waiting too long. Note the usable share of the window can also be raised by lowering `reply_limit` for someone whose replies are short.
- **Dropping turns in larger steps** (hysteresis), so the start of the prompt stays the same for several turns and Ollama can keep reusing its work; today each turn that pushes an old turn out changes the start and pays the processing again. A refinement to weigh once the wait is felt.
- **The context meter** (the percentage under the chat box): the engine's own count of the full prompt over the window, CLI first; the web UI waits for the dashboard work. The runtime's reported count cannot be the source (it is post-cut). Built as ADR 018 (CLI only).
- **Marking a truncated reply in the session record.** A reply that stopped at its length limit is marked on screen (`ModelReply.truncated`, the header) but saved to the record as written, so a half-finished reply is sent back as history on later turns.
- **Per-persona window and reply-limit overrides.** The window and `reply_limit` are global settings today.
- **A CLI settings screen.** `context_window`, `reply_limit`, `show_trim_notice` and `show_grounding` live in the settings file (`show_grounding` also has `/grounding`); `/settings` is still a placeholder, and a slash command per knob was deliberately not added.
- **A second look at the token margin and the recall result on other models.** The 15 percent margin was measured on one model's tokenizer; the recall test covered one model up to half its window, planted facts only, not facts spread across turns. Cloud models and other local models, and how the cold wait behaves after Ollama's keep-alive expires, are unmeasured. The `gemma4:e4b` memory readings did not make sense and are not trusted.
- **Known rough edges.** With both header notices showing at exactly 80 columns the header runs a few cells over and wraps; a very long answer from a reasoning model can spend the whole reply limit thinking (a clear error, or a marked truncation); the model's-maximum cache lasts for the process, so re-pulling a model tag with a different context length is not noticed until restart; a lookup that returns no maximum without raising is repeated each turn (a local call).

## Alternatives rejected

- **Do nothing and rely on Ollama's default cut.** Rejected on the measurements above: it removes the oldest turns first and can remove the soul and the grounding rules, silently.
- **Only raise the window.** Delays the problem and costs memory for everyone, and a longer chat still reaches any fixed window.
- **Keep the 20-turn cap as the only guard.** A count is not a size; 20 long turns overflow, 20 short ones leave most of the window unused.
- **Trust the runtime's own truncation, or ask it for the model's whole native window.** The first is the measured problem. The second would ask a model with a very large maximum for a very large window and its memory by default; the setting is the ceiling instead.
- **Shrinking the window by a fixed share (say 30 percent) because models handle long prompts badly.** Not chosen: recall held up to half the window on the model measured, the prompt already uses about 65 percent of the window, and the window costs memory, not time. The real cost of a long prompt is the cold wait, which a history budget bounds directly.
- **Read the runtime's token count for the meter.** It is post-cut and cannot show the overflow it is meant to warn about.
