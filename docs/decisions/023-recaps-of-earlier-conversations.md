# 023 — Recaps: picking up where the last conversation left off

> **Status: Proposed.** Built. Builds on ADR 006 (the session log), ADR 015 (the context budget), ADR 017 (the small background model call) and ADR 020 (where the prompt puts things). Implements the first, smallest part of the vision's "Sessions & memory" (a session's own summary, not yet durable facts or search across sessions). **Scope of every model figure: Ollama and `gemma2:9b` only.** Measured on invented conversations in scratch profiles; nothing of anyone's own sessions was used.

## Context

Every conversation is saved as a session log (ADR 006), and nothing reads it back. Each launch of the CLI is a new session, so the persona starts every time knowing only the vault. Asked "what were we working on last time?" or "arent you supposed to review our session logs?", she cannot answer, and in a real conversation she agreed she should have and confessed to lapses that were not lapses (ADR 022). ADR 022 made her say plainly that this is not built. This ADR builds the smallest useful part of it: a short recap of each earlier conversation, written by the persona's own model, that she reads at the start of the next one.

What the user asked for: picking up where they left off, written freely (no approval step), kept in the persona's own folder next to the sessions.

Two facts shape the design. The persona's earlier replies are not reliable evidence: some were wrong, and a recap that repeats a wrong reply makes it look like a fact about the user's work. And the model is small, so anything it writes has to be visible and easy to correct after the fact, since there is no approval before.

## Decision

**The roles.** The session log stays the source of truth and is never rewritten: it holds every turn word for word, it is what rebuilds the current conversation's history each turn (trimming for the window changes only what is sent, not the file), and it is what a person reads to see what actually happened. A recap is derived from it: small enough to hand to the model, cheap to read, editable, and safe to lose, since it can be written again from the log. Whatever later reads the past (search across sessions, durable facts, archival to a vault note, the record of grounded notes) reads the log or sits beside it, not a recap.

**What is written.** One plain markdown file per recapped session at `profiles/<handle>/recaps/<session id>.md`, beside `sessions/` (in the whole-vault fallback mode, where sessions go in `./sessions/<handle>/`, at `./recaps/<handle>/`; both are gitignored, so a recap is never committed, ADR 001). The session's id, and so its date, is the file name. The file is a header line `<!-- turns: <n> -->` and a few sentences: what the user was working on, what was left open, and anything the user said they had decided, in at most about 80 words. **The model is given only the user's messages, not the persona's replies.** The first version gave it both with an instruction not to record what the persona claimed; asked to remember a birthday it had never been told, the persona answered "I've saved your birthday, March 3rd", and the recap then said the birthday was March 3rd in 5 of 5 runs. With the user's messages alone the same conversation gave a correct recap 5 of 5. The price is that what the persona found in the vault is not in the recap (the vault has it anyway).

**Which sessions.** Of the ten newest sessions, the three newest that have at least two turns and have been quiet for half an hour are looked at (so a few throwaway sessions cannot starve a real one), and each gets a recap when none exists (or the one that exists covers fewer turns than the session now has, so a resumed session is refreshed). The model may answer `NONE` when there is nothing worth carrying over (greetings, small talk, a test message); that is stored as the header with no text, which means "looked at, nothing to carry" and is not tried again (a file emptied completely has no header, so it is the user's and stays empty). A session updated in the last half hour is left alone: it may still be running in another window. A very long session is recapped from its last 40 turns. A recap is saved whole or not at all (written to a temporary file and renamed), since a half-written empty file would read as the user's own and never be rewritten. A file that has lost its header line was edited by the user, is theirs, and is never rewritten.

**When.** Not at `/quit` (a blocking model call there made quitting hang once, and it would not cover a crash or Ctrl-C). When the CLI starts, one background thread calls `recap.refresh(handle)`, which does the work above for the persona; the user is typing their first message meanwhile. If it is not finished when the first message is sent, that turn waits for it (below). The function is the engine's, so the dashboard or Slack can call it the same way later. It never raises into the chat: a failed call leaves the session without a recap and is retried at the next launch.

**Which model.** The one the persona's turns use, in the same window as its chat (so Ollama does not load a second model), with a reply cap of about 200 tokens. A reasoning model is skipped, as in ADR 017, because it would spend the cap thinking. What goes in is the user's messages, the newest that fit the window, each cut to 1000 characters. A knob `session_recaps` in settings (on by default; only an explicit `false` turns it off) is for anyone who does not want the extra call, which matters most with a paid cloud model.

**How she reads it.** The two newest non-empty recaps, other than the session being run, go into the last user turn, above the notes, under a label that says they describe what was talked about and are not facts about the vault. Each carries its date and is named "Last conversation" only when it is the recap of the most recent earlier session of all; when that session had nothing to carry over, or no recap yet, every recap is called "An earlier conversation" (found in review: naming by position called an older one "Last conversation"). The newest is put last. A small model has no idea what day it is, so with dates alone "last time" was any of them. With the newest first and dates only it described only the older conversation in 3 of 5 answers to "what were we working on last time?" and in 3 of 5 to "where did we leave off?"; with the newest first and the names 4 of 5 answers to the second were the older one; with the newest last and the names, 5 of 5 and 5 of 5 (then 15 of 15 each), because it leans on what it read last. With the final wording (8 runs each) 8 of 8 and 8 of 8; when the last conversation had nothing to carry over and the two recaps are called earlier ones, "what were we working on last time?" gets the newest recap 6 of 8 times (twice she was vague or named the older one). `HOW_YOU_WORK` changes in the same commit: it no longer says she has no memory between conversations, but that she keeps only the recaps shown with the message, when there are any, and otherwise nothing, and that she does not learn. "We decided" still means the notes in the vault. Under pressure on the window the recaps are the first thing left out (before older turns and before note passages), since they only matter for a question about the past, and when they are left out the turn says so instead of implying there were none, as it already does for passages (ADR 015). A message sent straight after launch waits up to 20 seconds for a recap still being written (see below), so that the message that most needs it gets it.

**Where the block sits.** *Moved to the system prompt by ADR 026: beside the message it made her comment on a chat instead of continuing it.* Originally in the last user turn, as the notes do (ADR 020). Put in the system prompt instead, it did as well: 15 of 15 for each placement on "what were we working on last time?", "where did we leave off?" and a greeting that must not mention it. So it is not decided by that; the last turn keeps the system prompt the same on every turn.

**Waiting at launch.** The refresh is one small model call on the model the first turn needs anyway. Measured on this machine (three runs each, first-reply times to first token, noisy): cold model, no recap 8.6, 8.0 and 12.0 s; a recap started at launch and the message sent at once 11.2, 12.7 and 15.4 s (the message queued behind the recap call, about 3.6 s more); the message sent ten seconds later 7.0, 7.8 and 7.7 s (the recap call had loaded the model while the user typed, about 2 s less than none); model already warm, 6.1, 10.6 and 8.6 s without and 8.8, 14.5 and 10.8 s with a recap at once. In the message-at-once case the turn was queued behind the recap on the GPU anyway, so it now waits for the refresh explicitly (at most 20 seconds, then it goes without): the cost is the same and the turn gets the recap. A turn on a persona with nothing running does not wait at all.

**Where it lives in the code.** `engine/recap.py` reads and stores recaps, `engine/recap_refresh.py` writes them and runs the background refresh, and the prompt text moved to `engine/prompt_text.py` (the layout stays in `engine/prompt.py`, which re-exports the text) to keep each file under the 200-line cap.

**What else changes with it.** The reference notes (ADR 019) that said she reads nothing of past conversations ("Not built yet", "Privacy and data", "Personas", and the stale minimum in "Settings") are updated in the same commit: what she has (short recaps, not the logs), where recaps live, how to correct one (edit it, or empty it to stop a recap coming back, since deleting the file makes the next launch write a new one), that a cloud model is sent the user's messages to write one, and the `session_recaps` setting. Without this she answered "nothing reads those back to me, so I don't remember past chats" with recaps in front of her.

## Consequences

- She can answer "what were we on last time?" from something real, and the false confessions have a true answer to give instead.
- One extra small model call per finished session, in the background, on the model already loaded. On a local model it is free in money and costs some GPU time, which queues behind the user's first turn on a machine with one GPU: measured above, about 3 to 4 seconds more when the first message is sent at once, and none (even less, the model is already loaded) when it is sent ten seconds after launch. On a cloud model it is a paid call, hence the knob.
- The recap is a claim by a small model, kept between conversations. It can be wrong, so it is written from the user's words, labelled as a record of conversation, plain text in a place the user can open, and its origin (session and date) is its file name.
- The prompt is larger by up to about 400 tokens on every turn that has recaps (a recap is read back at up to 800 characters). At the smallest window (2048, ADR 015) that is a real share of the room, which is why the recaps go first when space runs out.
- Recaps are on by default, and are written by the persona's own model, so for a persona on a cloud model each launch (and each switch to that persona) can send the user's messages from up to three earlier sessions to the provider, which were sent before but are sent again, and costs tokens. `session_recaps: false` stops it; this was decided: recaps are on by default for every model, local or cloud, and `session_recaps: false` is the way out. Defaulting to off for a cloud model, which would keep "local by default" and never spend a paid call unasked, was considered and not chosen.
- The prompt text that says she has no memory changes from an absolute to a conditional, so a bug in reading recaps would show as her denying something she has, not the reverse. The live cases must cover both.

## Measured (`gemma2:9b`, five runs unless said)

- **Writing a recap** (`recap_quality`, four invented conversations, user's messages only): a working session 5/5 (names the project, the pending item and the stated plan), two greetings 5/5 `NONE`, the unfounded-claim conversation 5/5 without the invented date, a stated decision 5/5.
- **Reading** (through the real `run_turn`, two invented recaps): "what were we working on last time?" 5/5 the newest, "where did we leave off?" 5/5, "do you remember what we talked about before?" 5/5, "arent you supposed to review our session logs?" 5/5 saying she only has short recaps (after the reference notes were updated; before, 0/5 said so), a vault question about a project 5/5 and a vault question about an unrelated topic 5/5 without the recaps leaking in, a greeting 4/5 then 15/15 (one reply mentioned the earlier talk unprompted).
- **Saying what she has when asked about the logs:** 5/5, 5/5, then 6/8 with the final wording; the failures said she only sees the current chat, which denies the recaps she has. The sentence in `HOW_YOU_WORK` was compared against the old absolute one and against a stricter one (8 runs each on six cases without recaps): no reliable difference except that the stricter one made "what did we decide about the tax filing deadline?" worse (2/8 against 5/8), so the wording stays.
- **Not solved:** asked "what did I decide about the backups last time?" when the recap says it is still open, she says so in about 2 of 5 answers; the others say she does not remember or cannot find it in the notes (she treats a recap as one of the user's notes), and none invents a decision. This is in `live_prompt_cases.py` as a case that is expected to fail part of the time.

## Alternatives rejected

- **Putting the last session's raw turns in the prompt.** Needs no model call and no file, but it repeats her own past replies as if they were evidence, its size is whatever the user happened to say, and a two-line session is as prominent as a long one.
- **Writing the recap at session end (`/quit`).** Slow to quit, missed on a crash or a closed terminal, and the CLI is not the only channel.
- **Asking the user to approve each recap.** The user asked for it to be written freely. The safeguards are visibility and easy correction after the fact.
- **A vault note instead of a file in the persona's folder.** It would show up in the dashboard and the graph, but the retriever would also find it as a vault passage, so the same text would reach the model twice. The vision's session-close archival (a real note) is where that belongs, and it can replace this later.
- **Searching all past sessions.** Topical recall ("what did we say about X?") is a different problem with a different risk (old replies as evidence) and is left until real use shows it is needed.

## Not built yet

Out of scope: durable facts about the user (the vision's layer 2, a `memory.md` that ADR 001 already keeps out of version control), search across sessions, archival to a vault note, sharing recaps between personas (each reads only its own sessions), showing recaps in the dashboard, showing which recaps reached each turn (they are recorded, ADR 025), and any measurement on a model other than `gemma2:9b`.
